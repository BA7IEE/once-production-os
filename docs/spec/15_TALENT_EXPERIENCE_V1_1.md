## 0. 发给开发 Agent 的执行指令

你正在修改一个已有业务底座，而不是新建模特经纪平台。首先读取仓库当前 `AGENTS.md`、`docs/spec/AGENTS.md`、PRD、开发说明和本文件，并核对实际 HEAD。

**本轮业务目标只有一条主线：**

`收集人才 → 邀请本人 → 同档认领 → 本人维护 → 内部快速筛选 → 组成候选 → 受控发给客户`

模特是首个做深的类型；摄影、剪辑、翻译、化妆等共享身份、账号、来源、媒体、权限和邀请基础，但使用各自的业务表单。

实施时必须遵守以下六项：

1. 保留现有 Person ID、多职业关系、来源与字段依据、媒体原件、安全回执、删除和恢复机制；允许必要的增量扩展，不能把“保留底层”解释为“不准修改底层”。
2. 外部人才账号不加入内部 Membership；客户分享访问者不成为内部 VIEWER；Agent 不使用管理员账号冒充人操作。
3. 统一正常用户的新增、找人和详情入口。Person、TalentProfile、Fact、Evidence 等内部拆分不能继续要求用户手工串起来。
4. 每个业务工作包最终交付可操作页面、接口、权限、异常处理和运行证据；允许拆分内部迁移或安全基础子 PR，但未闭合旅程前不得对真实外部用户开放，不以“有表、有 API、有测试名称”代替完成。
5. 本规范明确扩大旧一期的范围；先回填主文档和精确调整门禁。不得直接删除安全测试，也不得让旧“禁止自助门户”条款永久阻止用户已经确认的新需求。
6. 未配置真实供应商时保持功能开关关闭，标记 `PROVIDER_NOT_VERIFIED`。不得使用万能验证码、自动通过身份核验、公开 COS 桶等方式使演示看起来可用。

第一轮交付应给出：基线差异、文档回填、变更清单、迁移计划、测试清单以及首个可运行切片。不要再次向用户询问已经确认的十项产品方向。

## 1. 第一性原理：这个系统到底管理什么

### 1.1 真正的对象不是“模特表”，而是同一个人的可使用资料

业务中同一个人可能同时是模特、演员和 KOL；资料可能由员工、Agent、本人或经纪人先后提供。系统要解决的是三个问题：谁是这个人，谁能维护哪些内容，当前哪些内容可以用于哪种场景。

据此分清五种不同概念：

| 概念 | 含义 | 不能混同于 |
|---|---|---|
| 人物身份 | 稳定的 `Person`，承接历史关系 | 登录账号、某次导入行 |
| 维护资格 | 谁能维护这个人的指定内容 | 内部员工权限、照片所有权 |
| 资料事实 | 姓名、量尺、作品经历等有来源的内容 | Agent 猜测、授权声明 |
| 使用许可 | 是否可以内部整理、给客户看、官网公开 | 本人已登录、文件已经上传 |
| 业务选择 | 某次候选、客户偏好、某次报价 | 预订成功、永久绑定、实际合作记录 |

**推导：账号绑定不复制档案；审核不等于官方认证；作品集不等于实际 ONCE 项目；客户喜欢不等于锁档；外部分享不等于公开上网。**

### 1.2 四类操作者，三种主要使用端

| 操作者 | 主要任务 | 主要入口 |
|---|---|---|
| ONCE 员工 | 建档、找人、审核、组织候选、报价 | 内部 Admin |
| 人才本人／经批准的代管人 | 认领、补充、更新本人资料 | 手机优先的 Talent Portal |
| 外部 Agent | 按授权接收的资料提取、去重提示、提交结构化草稿 | 有范围限制的 Ingestion API；MCP 可后接 |
| 客户访问者 | 查看指定候选、表达偏好 | Casting Share 页面 |

官网是审核后的发布渠道，不是上述任一端的数据库，也不是事实源。

### 1.3 六条不可变业务原则

- 一个人在同一工作空间内有一个主档；重复候选需要人工确认合并，不按同名直接归并。
- 一项新声明能被保存，不代表马上替换已有认可的事实。
- 内部可见、客户可见和官网公开必须分别判断；绝不能用一个 `isPublic` 包办。
- 媒体文件、资料描述和对其使用的许可分别管理，但在使用时联合校验。
- 前台操作按“上传模卡、添加案例、更新资料”组织，不按底层数据表组织。
- 未知就是未知；缺少价格不等于免费，未填写档期不等于有空，国籍未知不等于国模。

### 1.4 不做的事

本轮不做开放交易市场、平台抽佣结算、支付、合同生成、完整 CRM、自动竞价、经纪排他协议管理、排期锁定、订单预订或通用工作流引擎。也不做系统内微信笔记抓取、PDF OCR、任意网页爬取或“AI 自动认证人才”。

这些非目标不影响交付已确认的参考报价、可用时间、客户选择链接和本人资料维护。

### 2.2 造成后台难用的具体位置

`apps/admin-web/src/main.tsx` 的 `People()` 同时暴露“新建人物”和“新增人才”，分别使用 TD2 与旧建档路径；常规列表使用 `person.list`，另有弹窗式 `TalentSearch` 使用 `td2.person.list`，候选工作台又调用 `talent.search`。详情先进入 `PersonDetail`，再打开 `TalentWorkbench`。列表使用姓名字头而非模特封面。（证据 E02–E04，见附录 A）

问题不是系统“完全没有卡片”，而是**已有卡片没有以视觉选人组织内容，三个查询入口语义不一致，专业信息需要二次进入，技术维护操作占据正常业务位置。**

### 2.4 对上一轮结论的校正

**“底层不用推翻”成立，但“底层直接够用”不成立。** 特别是媒体多来源、外部操作者、展示授权和查询规模需要实质改造。

**“作品模型可复用”成立，但“案例字段齐全”不成立。** 当前 Work 没有独立案例年份、案例品牌和外部作品地址等完整结构；Project 的品牌关系也不能直接当作 Work 的品牌关系。[E12]

**“有机器账号”成立，但“已有完整外部 Agent 工作流”不成立。** 服务端当前对带 Authorization 的请求要求 TD2 路由，二进制上传走内部 Cookie 认证。新增摄取接口必须同时更新外层入口和细粒度权限。（证据 E07、E10、E11、E17，见附录 A）

**“分享快照不随普通编辑变化”不代表快照可以绕过撤回。** 必须同时满足内容版本固定和当前许可仍有效。

**“专业模特／素人”不应复用语言能力等级中的 `PROFESSIONAL`。** 它是模特职业下的业务分类，不是通用认证等级。

## 3. 需求冻结与发布边界

### 3.1 用户已确认的目标

| 需求 | 验收结果 |
|---|---|
| REQ-01 邀请与自助加入 | 员工能生成链接及二维码，人才从手机完成加入 |
| REQ-02 已有档案认领 | Agent／员工先建档，本人绑定同一个 Person，不重复新增 |
| REQ-03 长期维护 | 本人以后能再次登录，更新基础资料、模卡、照片、视频、案例 |
| REQ-04 组合找人 | 模特类型、性别、年龄、业务市场、城市、量尺、标签等可以组合筛选 |
| REQ-05 视觉资源库 | 大照片、核心属性、快捷筛选、一个主详情入口 |
| REQ-06 多身份 | 同一人多职业；角色专属字段不污染其他职业 |
| REQ-07 分层展示 | 内部、指定客户、官网公开分别授权和审核 |
| REQ-08 客户选人 | 候选链接、精选内容、客户偏好反馈，不暴露内部内容 |
| REQ-09 分层价格与动态资料 | 自报价、内部议价、客户报价分开；档期有来源和更新时间 |
| REQ-10 多人才扩展 | 模特先完整交付；通用账号及资料链支持翻译、摄影等 |

### 3.2 发布分组，不得把阶段完成说成全部完成

- **Release A：收人与本人维护闭环。** 内部模特库、目标认领和通用加入、手机资料维护、媒体上传／播放、案例、审核、基本筛选、Agent 摄取。它直接解决用户原始三项痛点。
- **Release B：客户选角闭环。** 在 A 上增加参考报价、基础可用时间、候选分享、许可与精选媒体、客户反馈。
- **Release C：官网受控展示。** 人才自愿授权、内部批准、发布投影、CMS 同步与撤回；不扩成营销自动化项目。

C 仍是确认后的目标，不是占位功能；但 CMS 未完成不得阻止 A 的内部收人与维护验收。B、C 未完成时必须如实标记剩余范围。

### 3.3 本文给出的默认决策

手机优先 H5，不先上小程序；内部入口保留，人才端独立构建；初期同 Origin 分路径部署；邮箱验证码作为外籍人才可用的基础认证方式，手机号验证按配置接入；不以“中国大陆手机号必填”阻塞加入。微信登录不是 A 的前置依赖。

每条面向真实用户的认证渠道都必须完成真实发送验收；若邮件未配置，该渠道不能显示“验证码已发送”。初期不接微信登录，不代表不能在微信内打开邀请链接。

## 4. 目标使用旅程

### 4.1 员工／Agent 先建档，再邀请本人

1. 员工点击“新增人才”，选择模特，填写姓名即可保存草稿；系统默认建立 Person、TalentProfile 与 `model` 职业。没有已选来源时，只创建真实归因于当前员工的“手工临时整理”来源，沿用 TEMP_ORGANIZE 的既有保护范围和期限；不能默认成模特已授权或来源已核验。
2. 或外部 Agent 提交一份摄取草稿，附明确来源与字段值，不先假定其内容已获核验。
3. 系统展示疑似重复和缺失字段；明确关联既有 Person 或建立新 Person。原始材料不足也允许保存，不要求假填年龄、国籍或量尺日期。
4. 员工从该档案点击“邀请本人维护”。可以绑定预期收件邮箱／电话；没有可信收件标识则使用“待人工确认认领”模式。
5. 本人打开链接，登录／验证后申请认领。系统校验邀请目标和接收人匹配，而不只是“对方有一个能收验证码的手机号”。
6. 认领成功后不改变 Person ID、历史作品和原始来源，不转移内部维护责任成员，不授予内部范围访问权。
7. 本人看到允许其查看的资料，不看到内部备注、来源原文、底价、客户报价或员工审核历史。
8. 本人修改并提交，员工一次查看整批差异并确认；审核通过的内容进入正式筛选。

### 4.2 发一个通用加入二维码

这是招募入口，不是某个 Person 的认领凭证。CLAIM 与 ENROLL 的 UI、令牌用途、数量统计和数据库检查分别定义。

ENROLL 允许多个申请人使用，但只有完成认证并创建自己的加入申请，才占用一个有期限的申请名额；GET、inspect、邮件预取和错误验证码都不占名额。`usedCount + reservedCount <= maxUses` 在同一事务内成立，不能只在最终批准时检查、让已上传大量资料的人突然发现名额用尽。

**尚无 Person/grant 的首个申请也必须能工作：** 为已验证账号创建 `TalentClaim(kind=ENROLL, targetPersonId=null)`，记录 admissionUntil、reservedAt、申请类型 SELF/GUARDIAN 和稳定 applicantKey，再创建关联的 Submission。申请人仅凭“自己拥有的有效申请＋Submission”维护其自己新提交的文字和暂存文件，不获得任何既有 Person 的读取权。这里不创建虚假 Person、临时 Membership 或假 grant。

SELF 申请在 workspace＋account 下最多一个未结束的加入主申请；重复扫码、换一条招募链接或换 commandKey 仍返回该申请，不重复建档。GUARDIAN 每个 child applicantKey 独立申请、分别核实；普通 SELF 不可借此创建多人档案。验证手机号/邮箱只是账号认证，监护人资格仍须另审。

已有有效 SELF 绑定时进入自己的资料；已有待审申请时进入该申请。内部发现疑似现有模特时，不给申请人展示候选人名单，也不能仅凭“员工选中了同名人”把已有档案授予申请账号：关联既有 Person 必须走与 CLAIM 相同的归属检查。通过后一次事务完成最小已批准身份资料、新建或精确关联 Person、grant、申请决定和名额 reserved→used 转换。失败不扣名额、不新增副本。

名额默认预留 7 天且不得超过邀请期限；预留失效后不再允许新上传/提交，但申请人可查看或删除自己的尚未到保留期限的草稿。重新取得有效邀请并显式续办可恢复申请。邀请撤销阻断未获批准的继续加入，不撤销此前合法完成的维护授权；确需撤销维护必须单独处理 grant。

草稿自身保留期与申请名额期分开，见 10.8；后台应提示名额到期和续办方式，不能偷偷销毁用户已填资料。

### 4.3 模特自己维护

手机首页显示“我的资料”“资料完整度”“上次更新”“待审核内容”。业务分区为基本资料、模卡与量尺、照片视频、作品案例、参考报价、可用时间和授权设置。

“添加模卡”完成文件选择、上传、归类及挂接；“添加案例”完成标题、角色、品牌／年份可选项、素材与提交。用户不需要先去素材库上传，再回到另一个页面创建集合。

保存草稿后退出，再登录可继续；提交后展示本次修改与状态。审核退回说明原因，不能把整份已通过资料变回空白。

### 4.4 员工选人并发客户

员工进入“模特”，选择筛选条件，勾选候选，加入某项目候选清单；在该清单选择客户可见字段、图片／视频和可选客户报价，检查展示许可，再生成客户链接。

客户在手机上看照片、模卡数据、精选案例和可播放视频，表达“感兴趣／暂不考虑／未选择”，可留言。系统明确提示“仅表达候选偏好，不构成确认档期或预订”。员工能看到反馈，不需要客户成为 ONCE 内部成员。

### 4.5 常见异常也属于主旅程

邀请过期、已被认领、收件人不匹配、扫码后切换账号、上传中断、照片格式不支持、提交后失去响应、资料待审核、来源失效、素材撤回、候选版本变更，都必须有可理解的处理入口，而不是只弹出英文错误码。

## 5. 信息架构与页面要求

### 5.1 内部导航

主要业务导航：**人才库、候选清单、作品库、项目库、审核收件箱**。

“人才库”下按职业切换模特、演员、KOL、摄影、化妆、翻译等。来源、机器接入、合并、审计、导出、删除影响和成员权限移到“管理与设置”，保留原有能力和授权检查，不删除。

不得继续并列“新建人物”和“新增人才”。普通联系人作为明确次级场景保留：创建时不建立 TalentProfile；不能强迫所有人都成为人才。

### 5.2 模特目录

默认照片网格，可切换紧凑列表。首屏筛选只保留常用项：业务市场分类、性别、从业类型、年龄段、城市、身高及拍摄类型。更多筛选折叠展开。

卡片至少显示封面、艺名、城市、从业类型、业务市场分类、身高；缺失值显示“未填写”。可选显示资料更新、待认领、待审核标识，但版本号、UUID 和技术核验说明不得占据主视觉。

无照片用明确占位，不生成虚构头像。选择封面时必须从该人才允许使用的媒体中选；不能使用任意全库 assetId。

勾选卡片不打开详情；打开详情不丢筛选条件、分页和已选候选。刷新和浏览器返回可恢复非敏感的页面状态；不得把整份档案、联系方式或价格写入 URL／浏览器存储。

### 5.3 主详情

一个主详情页直接呈现：概览、模卡与量尺、照片视频、作品、参考报价、可用时间、联系／经纪。当前角色不相关的表单不出现；必要时切换职业。

“资料来源、修改依据、历史、权限、旧数据复核”放在高级管理抽屉。后端可返回权限位和状态，前端不靠“有没有按钮”承担权限控制。

### 5.4 审核收件箱

按“某人一次提交”聚合，不默认铺满逐字段证据条目。展示旧值、新值、来源类型、媒体缩略图和冲突提示。支持整批通过、整批退回、选择字段通过；有关系依赖的一组修改必须原子处理，例如案例与署名、量尺与当前量尺指针。

`接受资料作为当前声明`、`人工确认字段与来源一致`、`核验成年／证书`是不同操作，不得用一个“全部认证”按钮合并。

### 5.5 手机端硬要求

在 360–430 CSS 像素宽度可完成加入、认领、填写、上传、排序和提交；不能依赖桌面悬浮操作。上传有逐文件状态、失败重试和取消；多文件选择应支持继续填写其他区块。

界面具备中英文固定文案，字典使用现有 `labelZh/labelEn` 能力。自动翻译介绍文字仍为草稿，不能改变原始事实或客户可见状态。

## 6. 领域模型：增量扩展，不建设第二份人才事实库

### 6.1 现有身份与职业保持不变

`Person → TalentProfile → PersonRole` 继续为主链。

一个账号可以依法定／经批准的代管关系维护多份人才档案，例如监护人维护两个孩子；这不代表允许普通模特账号任意绑定多人。数据库用授权关系表达，不使用 `TalentAccount.personId` 的永久一对一字段锁死扩展。

同一 Person 只允许一个 ACTIVE SELF 主维护绑定；同一工作空间内，同一 TalentAccount 也只允许一个 ACTIVE SELF 绑定。GUARDIAN 或经批准的经纪代管可维护多人，逐 Person 独立授权。一个人是否专业、参考价格、可接拍类型均绑定相应 PersonRole。

### 6.2 最小新增持久化资源

下表是建议落表方案。已有结构可复用的位置已明确；不要为了抽象再做一套无类型 EAV 表或通用实体引擎。各表均需工作空间隔离、稳定 ID、revision、createdAt、updatedAt；秘密和审计记录另按安全规则处理。

| 资源 | 关键字段及约束 | 首次交付 |
|---|---|---|
| `TalentAccount` | workspaceId、displayName、status、sessionEpoch；不是 Membership | A |
| `TalentIdentity` | accountId、provider、规范化标识的 keyed hash、加密原值、verifiedAt；验证码验证不等于人物归属验证 | A |

| `TalentAccessGrant` | personId、accountId、relation=SELF/GUARDIAN/AGENT、允许动作、状态、批准依据、授权 epoch；默认只开放 SELF，GUARDIAN 经人工确认 | A |
| `TalentInvitation` | purpose=CLAIM/ENROLL、targetPersonId 可空、tokenHash、secretVersion、预期接收人 hash、expiresAt、maxUses、usedCount、state、recoveryEpoch | A |

| `TalentConsent` | personId（ENROLL 时可空但须关联 claimId）、grantor、用途、字段/媒体范围、许可文本版本、有效期、撤回状态及时间；批准时同事务确定 Person，不换授权人 | A 内部；B 客户；C 公开 |
| `TalentDemographics` | personId、sourceId、性别、国籍代码数组、出生信息及精度；访问投影隐藏完整生日 | A |

**概念上的 Submission 不等于第二个正式 TalentProfile。** 草稿和待审内容只参与维护页面与审核，不进入正式搜索和客户展示；通过后写入现有事实体系，保留决定与来源引用。

`ModelProfile` 用于“模特这个职业”的业务属性；`CastingProfile` 继续承载现有发色、瞳色和当前量尺关系，不重复存量尺。

**量尺日期的明确增量：** 将 `MeasurementSet.measuredOn` 允许为空，`datePrecision` 增加 UNKNOWN，增加 `reportedAt` 表示系统实际收到声明的时间。EXACT_DAY／APPROXIMATE 必须有 measuredOn；UNKNOWN 必须不伪填 measuredOn。确认的是“当前采用的量尺声明”，不代表实际测量日期已核验。旧有日期、状态、历史指针原样保留，相关数据库检查和 TD2 schema 版本同步升级。

### 6.3 强约束

所有业务引用必须具有 workspace 外键语义；涉及人、角色、集合、作品、申请时验证归属。不能只在前端检查，也不能把“引用对象存在”当作“当前操作者有权使用”。

| 约束 | 数据库／服务行为 |
|---|---|
| SELF 双向唯一 | `(workspaceId,personId)` 和 `(workspaceId,accountId)` 分别对 relation=SELF 且 status=ACTIVE 建唯一索引；到期任务不及时不能产生双 ACTIVE，切换前先显式关旧授权 |
| GUARDIAN/代理多人 | 每份 grant 有独立 personId、scope、允许字段组、role 范围和审批依据；不受 SELF 账号唯一索引影响 |
| 邀请语义 | CLAIM 必须带目标且 maxUses=1；ENROLL 不带预先指定的目标；用途/目标/收件人改变必须轮换秘密 |
| 名额和申请去重 | used＋reserved 不超限，名额转换与批准同事务；同账号同申请的重试不重复预留；另换 key 不能绕过业务唯一约束 |
| 账号身份唯一 | 规范化身份 keyed hash 在 workspace＋provider 内唯一；同一个联系人为多个孩子代管时复用账号及不同 grant，不复制身份账号 |
| 未绑定暂存 | personId/sourceId 可空不等于匿名；必须有可验证的申请、Submission、真实 owner 和内部分配的审核范围 |
| 职业与素材 | ModelProfile 只关联 model 职业；素材条目和作品署名必须符合该 Person＋Role；未知码拒绝 |
| 客户反馈 | recipient 与 version 属于同一 share，entry 属于该 version；唯一键 `(workspaceId,recipientId,versionId,entryId)`，会话换发不复制偏好 |

不能在部分唯一索引中依赖 `now()` 判断有效期；ACTIVE 状态表达可索引约束，时间判定仍在服务中重查。其他关系也必须配套 FK、CHECK 或事务内语义校验；跨表业务语义不要假装一个 CHECK 就能表达。

账号状态、认领状态、资料状态、来源有效性、审核状态和展示状态分别表示。归档不等于撤回，撤回不等于物理删除。

### 6.4 生日、年龄与未成年人

出生信息使用一个明确分支：EXACT_DATE、YEAR_ONLY、DECLARED_RANGE 或 UNKNOWN。完整生日属于受限字段，不进入普通目录、客户分享或公开投影；不得把日期范围不确定性转换成伪精确生日。

DECLARED_RANGE 必须保存声明时的 `[minAgeYears,maxAgeYears]` 和 `ageAsOfDate`。年龄筛选统一先把来源转换为可能的出生日期区间，再按查询的业务日期计算完整的可能年龄区间；默认只有全区间符合条件才匹配。无法可靠解释的历史年龄/“20多岁”只显示原声明并列入需确认，不当作精确筛选值。YEAR_ONLY 同样按区间处理；不能拿今年的年龄范围永久使用。

年龄快捷项按版本化配置生成，首版建议 CHILD=0–12、TEEN=13–17、YOUNG=18–34、MIDDLE=35–59、SENIOR=60+，全部仅为业务筛选值。未知年龄不自动算成人，展示年龄范围不等于法律成年证明。完整生日查询/修改与一般 records.read 分开授予；返回年龄的逻辑不得顺带返回明文出生日期。

`AdultEligibility` 的 UNKNOWN／SELF_DECLARED_ADULT／VERIFIED_ADULT／RESTRICTED 继续独立存在。填写生日或批量批准量尺都不能设置 VERIFIED_ADULT；只对确需成年限制的内容使用独立资格门，不要求所有普通模特先上传身份证。

产品默认未满 18 岁由经确认监护人维护。定向邀请的接收渠道匹配不能越过这条限制：已知或申报未成年时不自动生成 SELF grant；未知年龄可以先创建仅能提交新材料的申请，由本人声明或内部核实后决定绑定，不能凭照片推断。发现新资料与已核验成年资格冲突，先禁用成人限定用途并产生人工复核任务，不自动删除资料，也不静默保留成人用途资格。

满 18 岁不自动把监护账号变成本人账号；本人接管需独立认证、归属确认、记录交接、关闭旧的受影响授权。现存非冲突的其他代管关系按明确决定处理。这里 18 岁是本方案产品门槛，不替代具体法律适用判断。

### 6.5 国模、外模与国籍

`castingMarketCode` 是 ONCE 业务市场分类，如 DOMESTIC、INTERNATIONAL、UNCLASSIFIED；`nationalityCodes` 是明确来源的国籍声明。两个字段不能相互替代。

快捷按钮显示“国模／外模”可以满足业务习惯，但存储稳定代码，并在录入说明中解释分类。国籍变化或补齐时可以提示检查市场分类，不能无提示改写。国籍未知不默认分到国模，不能按长相、姓名或工作语言自动推断国籍、民族或血统。

从业类型使用独立的 `AMATEUR / PROFESSIONAL / UNSPECIFIED` 业务代码；需要“新人”时用可扩展业务标签而非硬写专业能力等级。分类由本人声明或员工记录，来源必须可追溯。

### 6.6 标签语义必须分开

| 维度 | 例子 | 含义 |
|---|---|---|
| 风格 | 自然、运动、时尚、商务 | 适合的表现风格，可由本人选择，员工整理 |
| 愿意参与的拍摄类型 | 平面、电商、走秀、广告等 | 当前接受的服务范围，不等于已有经验 |
| 作品内容标签 | 商业、美妆、生活方式等 | 某个集合／作品的内容性质 |
| 已有经历 | 某品牌外部案例、ONCE 实际合作 | 来自 WorkCredit 或 ACTUAL 项目事实 |

不能因为有一个 LINGERIE 集合标签，就自动认定“本人愿意接此类拍摄”；不能因为愿意接某类拍摄，就宣称拍过该类商业项目。

普通标签字典允许管理员维护名称和启停，code 不换语义。停用标签保留历史；检索、显示和新提交对停用的处理须一致。不为标签建设规则引擎。

## 7. 资料来源、本人提交与审核策略

### 7.1 现有约束必须正面处理

`sourceCurrent()` 使用来源状态、validFrom、validUntil 和 basisMode；普通内部使用要求 CONFIRMED。TD2 `patchFact()` 拒绝跨 sourceId 直接修改，提示提交字段建议；已确认量尺不可原地修改。`patchPerson()` 仍要求人物原来源可用。（证据 E09、E19，见附录 A）

因此不能把本人表单直接接到旧 `td2.person.patch`／`td2.fact.*.patch` 后就宣布完成。本人提供的新资料必须形成可独立追溯的新来源，能处理旧来源不再可用的情况。

### 7.2 首版明确选择：服务器草稿＋按次提交＋整批审核

Release A 采用草稿＋提交审核，不自动用本人最新输入替换正式事实。固定状态机：

| 状态 | 允许后续动作 |
|---|---|
| DRAFT | owner 以 expectedRevision 保存、上传、显式 submit 或撤回；草稿暂存有 TTL |
| SUBMITTED | payloadDigest 固定；内部决定，或 owner 撤回；任何人不能原地改 payload |
| APPROVED / PARTIALLY_APPROVED / REJECTED | 一次审核的终态，决定和条目状态固定；需要继续修改时 fork 新 Submission |
| NEEDS_REBASE | 当前提交不能直接采纳；读取自己可见差异，fork 新草稿并重新 submit |
| WITHDRAWN / EXPIRED | 不能再批准；内容按保留期限清理；需要继续时 fork，重新取得有效上下文 |

部分批准的语义是：**本次决定一次结束整份提交**。每个条目/依赖组得到 APPLIED 或 REJECTED，不存在“父单已完成、某些子项却仍可再次通过”的悬空状态；未通过项可一键复制为新草稿。拒绝理由不得向外部提交者回显内部底价、其他人身份或不可读原始依据。

采用条目依赖有向无环图和 dependencyGroup：量尺及其当前指针、案例与本人署名、集合及条目等必须整组接受，拒绝选中不完整依赖组，不用先写一半再让前端补。submit 时校验所有被引用文件技术 READY 且仍属于当前申请/人；未选入提交的多余文件继续留草稿保留期，不自动发布。

审核事务先检查当前身份、授权、来源、各目标基线和所有依赖，随后应用计划、记录来源及决定、统一更新父 revision 和回执；任一检查失败整笔回滚。owner 撤回与员工批准的竞态用 submissionRevision/CAS 决定，不能两边同时成功。撤回或退回不会清空已认可的旧档案。

低风险自动批准不在本轮默认开启。来源使用确认、字段与来源一致、成年/证书核验仍是三种不同业务决定，不设置“全部认证”。

### 7.3 本人来源的落地方式

保留 Source 的内部管理责任人，不把 TalentAccount ID 填入 `maintainerId`／`reviewedBy` 等 Membership 外键。

新增来源归因关联，记录提交账号／机器身份、submissionId、材料来源说明及相关 consentId。内部责任成员和 intakeScopeId 由后台配置产生；新申请默认进入限定审核范围，而非全部员工可见。审批必须同时具有暂存范围与目标 Person 范围的权限；维护责任不等于该成员亲自提供了材料。

草稿及待审材料使用独立的“外部提交暂存上下文”，不伪造 CONFIRMED Source。审核通过时，依据该次真实提交及内部使用同意，建立或确认相应 Source，再写入当前事实与 FieldEvidence。来源状态确认表示允许在该用途下使用资料，不表示每个职业经历、年龄或证书都已被认证。

**首版有效期方案：** 保持现有来源有明确 validUntil 的结构，不为了门户把所有来源变成无限期。可提供明确展示给提交者的内部使用期限，建议初始产品选项为 12 个月；这是待落地的产品默认值，不是现有规则或法定期限。实际 validUntil 必须与同意文本一致。以后续期需再次确认，不能由系统无提示续期。

账号和维护绑定不会因某份来源过期而自动删除。本人仍可登录、提供新资料和重新授权；已失效的旧资料不得被门户接口越权重新显示，也不能偷偷延长旧 Source 的期限。

**用途依据必须进入实际读策略，不能只存一张 Consent 表。** 新 Source 通过 SourceUseBasis 明确关联该次 consent/独立人工依据的版本、用途和字段/素材范围。统一 `canUseEvidenceForPurpose()`：检查资源保护、来源当前状态、所需用途及仍有效的依据；门户专用读规则另查 9.4。新的有用途依据来源不能因 `sourceCurrent()` 仍返回 true 就绕过 consent 撤回。旧来源的内部用途按旧真实依据保留，不强制伪造一份追溯 consent；旧内部依据不自动赋予客户/官网用途。

撤回在同一事务内关闭相应用途依据、递增保护/许可 epoch、失效关联发布资格。若某来源已无任何有效内部依据，则其内部使用也不可用；有经审核、范围明确的独立有效依据时，只保留该依据实际覆盖的内容。不得用“还有一个来源”保留无关字段或用一份撤回同意推定必须删除所有独立作品。

统一策略要接入新/旧人物列表、TD2 图/SQL、候选、作品、媒体原件/预览、AI 外送、导出和下载；不可修改的旧消费者在适配完成前关闭新数据入口。异步消息、缓存清理或 CMS 同步用于后续处理，不是下一次读取拒绝的前提。重新同意形成新版本，不能复活旧签发链接。

### 7.4 跨来源更新的处理

复用 FieldProposal 的“新来源不能静默覆盖旧来源”语义，并在 Submission 审核服务中批量落实。

不同字段的处理必须明确：

| 修改类型 | 行为 |
|---|---|
| 尚无值的新字段 | 经审核后新增事实及来源依据 |
| 原有值相同 | 记录新增独立支持依据，避免重复生成无意义业务版本 |
| 新值与原值冲突 | 显示差异，由有权限员工决定当前值，保留旧依据 |
| 已确认量尺更新 | 新建 MeasurementSet，审核确认后替换当前量尺指针，保留历史 |
| 人物原来源过期／撤回 | 经受控“采用新来源支持身份字段”流程恢复必要身份依据，不让普通 patch 绕过原有来源保护 |
| 本人提交成年／资质声明 | 只记录声明或未核验证明，不能自动设 VERIFIED_ADULT／VERIFIED |
| 本人新增 Work | 进入外部案例审核，不自动修改共享 Work 上其他人的署名 |

当前 FieldProposal 是单字段决策；新增批处理需要同一事务、明确关联依赖和完整回执，不得让前端串行调用几十次产生半张模卡。

实现 `TalentSubmissionReview.accept()` 时先校验所有基线与授权，生成有依赖顺序的变更计划，再写事实／关联／依据，最后更新聚合 revision 和提交状态。现有 createFact／patchFact 会逐次 bump Person：不能把同一个 expectedPersonRevision 机械传入循环。优先抽取事务内辅助函数，使父记录在整批应用后统一递增；保留旧单项接口语义。

原来源不可用时，新增受控的 `adoptIdentityFromSubmission` 路径：校验人物本身未删除／未合并、员工有目标范围和审核权限、新来源可用及提交归属；只采用新材料明确支持的身份字段，记录完整 FieldEvidence。不得从不可读旧来源复制内容。将独立身份依据判定共享给新目录、旧投影、候选和媒体等消费者。已核对 `Shortlists.ensurePair()` 仍直接读取人物主来源；只修新详情会出现“人能看却不能进候选”。必须按可证明的身份字段和相应新来源形成可用身份投影，相关消费者改用该投影，不重新启用旧来源，不无条件取消 sourceFor。旧来源历史不重写；不可读的旧姓名/别名/简介不能用于补全新值。[E05][E19]

后台审核新提交时，内部权限是调用授权，不是所有新数据都来自审核人。保留原 TalentAccount/ServicePrincipal 提交归因；新的 FieldProposal 如直接承载本人提议，应增加明确 TALENT 归因分支及外键，而不是把本人记成 IMPORT 或内部员工。

### 7.5 权限冲突与业务冲突分开

缺少访问权返回统一不可访问响应，不向无权用户解释“这是某位其他模特的数据”。本人有权访问但发生版本变化，返回 `409 REVISION_CONFLICT`，展示其有权看到的字段差异。

审核提交时逐目标记录 baseRevision/字段摘要及关系集版本。Person 总 revision 用于显示和聚合变更，但不能作为整批无条件冲突门；否则同一人的报价更新就会使完全独立的案例添加失效。保护 epoch、grant、scope 和状态变化仍必须整批重查；同目标字段、量尺指针或集合关系改变返回 NEEDS_REBASE。新增对象先校验相关业务唯一约束；不可通过更换 commandKey 重复创建。

一次批准成功后，原键重放应先查相同 principal＋operation＋key 的回执再核对可访问性，不再次使用已过期的输入 CAS 重新 apply。另换 key 请求同一个终态 submission 时，返回终态/已处理结果而不重复写事实。审核返回 `resourceId=submissionId`，条目结果和被创建对象的映射由专用提交详情读取，回执不保存整份模卡。

### 7.6 完整度不等于可信度

完整度只表示是否有姓名、城市、封面、量尺、至少一个资料集合等，不评判颜值、专业能力或合作价值。未核验的自述也可以算“已填写”，但必须保留来源与状态，不包装成已认证。

## 8. 邀请、认证、绑定与代管

### 8.1 定向邀请状态机

`DRAFT → ACTIVE → CLAIMED / REVOKED / EXPIRED`

EXPIRED 可以由时间派生，不要求依赖定时任务才失效。邀请重发产生新 secretVersion，旧凭证立即无效。变更目标人物、收件人或用途不能沿用旧令牌。

CLAIM 默认 7 天、单次使用；ENROLL 默认 30 天并有明确人数上限。ENROLL 保持 ACTIVE 直至撤销／过期／达到上限后 EXHAUSTED，不能在第一个人加入后设为 CLAIMED。这些是首版可配置产品值，不继承 RecordHandoff 的上限作为授权结论。

### 8.2 防止链接泄露后被陌生人认领

手机号／邮箱验证码只证明对该联系渠道的控制，不证明该人就是目标模特。

定向邀请应支持：

- 预绑定接收渠道：认证身份必须匹配邀请记录中的 keyed hash。
- 无可靠渠道：认证后创建 PENDING Claim，由员工依据实际联系确认，批准后才开放既有资料。
- 监护／经纪代管：显示代管关系并独立批准，不伪装成 SELF。

没有匹配收件人，也没有人工批准时，不得仅凭持有二维码立即取得维护权。

### 8.3 令牌与二维码

令牌使用至少 256 bit 密码学随机值，数据库保存 hash，设置用途、版本、期限和撤回状态。二维码在本地浏览器或自有服务生成，不把含凭证 URL 交给第三方二维码网站。

优先采用页面 fragment 承载初始令牌，如 `/talent/claim#i=opaque-id&t=secret`；前端通过受限 POST 交换上下文，并立即清理地址栏。邀请上下文保存在短时服务器记录并绑定相应 HttpOnly 预认证 Cookie；服务器返回非秘密 contextId，每次后续认领显式传 contextId，不能把 Cookie 中“最后打开的邀请”当隐含目标。多标签同时打开两人邀请时必须按各自上下文操作并显示脱敏目标确认。清理 fragment 后，可在页面地址保留非秘密 contextId 用于刷新，但它单独不能换取访问权；原 token 不转存到浏览器存储。此为拟定路径，不是已部署域名。禁止在分析日志、错误日志、Referer、埋点或错误上报中记录令牌。

GET 打开、邮件预览和聊天软件链接预抓取都不消耗认领次数。真正批准绑定才在事务中增加 usedCount／消耗定向邀请。

以上令牌防护参照 OWASP 对一次性 URL 凭证的随机性、限时、防泄漏和限流建议；认领归属判断则由本项目另行定义。[S01]

### 8.4 生成凭证的“结果未知”必须可恢复

普通“创建邀请记录”走现有 COMMAND 回执，仅返回邀请 ID 和版本，不把原始令牌放入回执。

“签发／轮换链接”是独立 SECRET 操作，返回原始令牌一次。若响应丢失，不能承诺从 hash 恢复同一链接；页面提供“撤销旧版本并重新生成”，保证旧版本失效。不得为了按钮方便将原始 token 塞入审计、localStorage 或命令结果。

ENROLL 和客户分享的链接也按这个原则处理；重复访问链接与签发秘密是不同操作。

### 8.5 原子认领

认领事务必须一起完成：校验登录账号及其 epoch、邀请状态／用途／期限／接收身份、目标 Person 状态、重复有效绑定、Claim 决定、维护授权关系、邀请消耗和命令回执。

同一账号同键重放返回同一结果。邀请已消费后，应先按当前账号核对既有回执，再判断是否可重放；不能让成功请求重试变成“已被别人认领”。已合法完成的绑定不会因申请用过的邀请随后到期而反向失败，但账号/grant 已撤销时仍拒绝读取受保护结果。另一个账号使用相同令牌时必须拒绝。

ENROLL 批准还要验证本人的有效名额预留、最小资料/同意、是否已有有效 SELF、同名目标的独立归属证明及实际审批权限；最终绑定、名额转换、内容最小采纳和回执同事务提交。批准人不是可以绕过人/账号归属限制的“超级角色”。

两个请求同时认领同一 Person：数据库唯一约束是最后防线；失败事务不能留下多余账号绑定、被错误消耗的邀请或半完成状态。

### 8.6 账号生命周期

验证码建议默认 10 分钟有效、同一 challenge 最多 5 次错误尝试；发送重试至少间隔 60 秒，并按渠道标识、IP 和工作空间分别限制小时／日额度。这些均为拟定、可收紧的产品参数，不是已存在配置。验证码 hash 使用带服务端密钥的方案，禁止万能验证码。换发新挑战后旧挑战失效；发送是否成功使用明确状态，不以排入队列冒充已送达。

身份规范化必须固定规则和测试，不能擅自去除邮箱 local-part 的点号／加号而合并不同地址。实际完成验证码校验后才能设置 verifiedAt；前端提交的“已验证”布尔值不能作为依据。

邮箱和手机号变更要求验证新渠道，必要时核对旧渠道；不能因两人共用一个经纪人电话自动合并 Person。手机号等身份标识的查重和检索使用带独立密钥的 hash，不使用可枚举的裸 SHA。

退出、暂停账号、撤销代管、人物进入删除流程、恢复隔离后，旧会话和未完成上传都须重新校验。一次账号恢复不得给该账号增加新的 Person 访问范围。

监护人可以维护多个孩子；每份授权均有明确 personId，不能因账号关联一个家庭就可读同姓人物。经纪人代管的批量能力可在后续开放，但关系模型从首版不能写死一对一。

### 8.7 认证挑战、发送与会话恢复的完整合同

验证码挑战绑定 workspace、purpose、规范化 identityHash、preAuthContextId 和创建浏览器的随机上下文。登录、绑定新渠道、恢复账号和认领上下文不能共用一条 challenge。预认证初始化、创建挑战、verify 和邀请 exchange 都验证精确 Origin；以预会话 CSRF token/自定义头及当前上下文防止登录前请求伪造。认证成功换发全新的正式 session，不能将预会话原样升级。[S03]

业务上必须同时区分：已排队 QUEUED、供应商已接收 ACCEPTED、供应商能证明的 DELIVERED、FAILED、UNKNOWN。没有送达回执时不写“已送达”；有效验证码的校验不依赖供应商一定支持 DELIVERED 回执。UNKNOWN 不盲重发；用户显式重新申请时受发送频控，并使前一同用途 challenge 失效。任何重发都不能刷掉累计滥用限制。

只有 codeHash 不足以让异步发送 worker 发送验证码。选定实现：AuthDelivery 保存**短期加密**的最小收件地址/代码载荷、challengeId、providerRequestKey、有效期和状态，使用独立消息密钥；网络发送在事务外进行，发送前再次检查 challenge 是否仍有效。普通日志/回执/业务导出没有验证码，发送终态或超时后清除加密载荷，恢复隔离时不补发旧验证码。状态机不是通用通知引擎。

verify 消耗 challenge 和创建账号/新 session 在一个事务内完成。响应丢失先请求 portal/me：已有 Cookie 则继续；没有有效 Cookie 时重新发起认证，不因“某 challenge 已消费”就给任意重放者签发 session。会话凭证不写普通命令回执。

新增 `X-ONCE-Talent-Account` 和 `X-ONCE-Casting-Recipient` 请求身份绑定：写请求携带页面读取的身份 ID，服务端与真实会话对照；它们不是认证凭证，不可取代 Cookie。跨标签换账号后旧请求不得以新账号身份执行。外部端沿用未知结果暂停/同身份核对的语义，重登录后的业务幂等主体仍是稳定 account/recipient，不是刚换的 session token。

失去全部认证渠道的账号恢复需要单独人工恢复流程及归属材料；新渠道验证成功不等于自动拿回旧账号。恢复后撤销旧会话、更新 epoch 并重新核对 grant，禁止用姓名搜索后把档案直接绑定给新邮箱。

## 9. 权限与接口隔离

### 9.1 保持现有内部 Actor，不冒充 Membership

基线 `Actor`、审计 actorId、回执 actorId、上传 actorId 主要按 Membership 建立关系，机器另有 ServicePrincipal。（证据 E06、E07、E10，见附录 A）

建议增加入口级别的认证联合类型：

```ts
// 拟新增类型，不是当前仓库已有接口。
type RequestPrincipal =
  | { kind: 'INTERNAL'; actor: InternalActor }
  | { kind: 'MACHINE'; actor: MachineActor }
  | { kind: 'TALENT'; actor: TalentActor }
  | { kind: 'CASTING'; actor: CastingViewerActor };
```

内部服务继续接收现有内部／机器 Actor；人才和客户接口使用独立处理器。要共享的校验下沉为明确的业务辅助函数，而不是把 TalentActor 强制断言成 Actor 或伪造一个管理员 Membership。

### 9.2 精确复用什么，扩展什么

复用验证工具、事务、基础记录、不可变历史、时间抽象和命令回执语义。

**本规范选定：扩展既有命令／审计记录，不建立第二套简化回执系统。** 追加 `principalKind`、有外键的 `talentAccountId`／`castingRecipientId`，保留现有 `actorId`（Membership）和 `servicePrincipalId` 的含义。COMMAND 的操作者必须恰好落在一种身份分支；系统事件仅在审计层允许独立 SYSTEM 分支，不能让匿名业务写入借用 SYSTEM。

幂等作用域固定为 workspace＋principalKind＋对应 principalId＋operation＋commandKey。历史数据按既有 actorId／servicePrincipalId 回填，不改变历史归属。审核决定记录真实内部审核人；本人提交和 Agent 摄取记录真实外部操作者，两者不得覆盖。

上传记录另增加明确的 uploader 分支，只允许 INTERNAL／TALENT／MACHINE，不允许客户会话上传。与 `workerActor()`、context、claim、heartbeat、finish 和失败/清理路径一起改造；worker 使用上传主体及当前 grant/submission/机器权限重新授权，而不是为外部上传找一个代理员工。

数据库回执和审计不能只新增可空列：COMMAND 必须用 CHECK 验证 principalKind 与四种 ID 的 XOR，对每类主体建立隔离的唯一索引；SYSTEM 仅用于真实系统审计，旧双空系统事件按其实际动作回填，不猜成某个员工。历史内部/机器回执保持原查找和重放结果，新增主体不参与旧 actorId=null 的歧义查询。`writeAhead()` 的 intentId 也必须使用相同稳定主体元组，不能让所有外部操作都落在 undefined membershipId。

必须同步修改 Prisma、核心类型、MemoryStore、审计写入、回执查找与重放鉴权、导出重建、恢复核对和删除扫描。不能只改 TypeScript 使其编译，也不能用 `as Actor` 使外部主体绕过授权。若后续需要改变此决策，必须提交替代 ADR 和等价的恢复／撤权证据，不在实现中临时混用方案。

| 读取本人可维护资料 | 按业务权限 | 限有效 grant 指向的 Person 与白名单 | 仅摄取上下文，不自动获得本人权限 | 禁止 |
| 提交个人资料草稿 | 允许 | 允许 | 允许 | 禁止 |

### 9.4 DTO 必须从允许项生成

分别定义 InternalTalentDetail、SelfTalentDetail、ClientCastingEntry、PublicTalentProjection。禁止展开内部对象后删除若干字段；每个投影从白名单和当前用途依据构造。[S02]

SelfTalentDetail 的数据可以来自：①本人拥有、仍在合法暂存期的 Submission；②已经批准供该 grant 查看/维护的正式资料。**“这是自己的 Person”不意味着可以读取该 Person 关联的所有内部来源。** 邀请或内部审核时记录 `selfExposureManifest`，只包含明确可向本人展示的字段/媒体版本、摘要及依据；manifest 属于 grant/审批记录，不复制整份内部档案。开放本人预填时再次核对这些依赖；内部备注、成本、第三方私人提供的未获开放材料、证件证明默认不在其中。

selfExposureManifest 不自动开放该 Work 的其他人物、客户信息、全部署名或原件。本人自己的合法待审内容可以读，但不能借查 submissionId 下载其他人文件。过期/撤回的正式内容不能借草稿镜像绕过；独立合法保留的自己提交记录仅按其暂存/个人查询用途显示，不重新投入业务筛选和分享。修正资料仍通过新声明，不要求把不可读旧值交给本人。

内部核验只能将“该信息由某人提供、被采纳”的状态输出给本人，不返回源证据全文、其他员工信息、全量 FieldEvidence。ClientCastingEntry 不含内部 Person/Account/Source UUID、对象 key、内部原文件名、内部价格及审核意见；对外 entry/media ID 是当前展示版本的不透明引用。

每个查询条件、排序及 facet 也要授权。没有内部成本权限时，连 `internalCostMin`/成本排序/成本计数请求都拒绝，不能只隐藏返回中的成本字段却允许据结果推测。完整生日过滤仅由有权限的内部业务查询转换为年龄条件，不在普通 DTO 暴露生日。

列表、总数、封面、字节、历史、错误与导出都执行同样边界；媒体内容的脱敏另见 15.2，JSON 白名单不能代替对图片/声音的检查。

### 9.5 会话与 Origin

建议初期同一个精确 HTTPS Origin，分三组 UI 路径：`/admin/*`、`/talent/*`、`/casting/*`。保留 `/`、`/activate` 的兼容入口，不在本次强制配置三个新子域名。

API 分发必须在内部 Application 认证前显式区分 `/api/v1/portal/*`、`/api/v1/casting/*` 与内部／Agent 路由。路由前缀按完整路径段匹配，例如 `/api/v1/casting/`；不得用不带边界的 startsWith 把内部 `/api/v1/casting-shares` 错分给客户处理器。未知或编码歧义路径拒绝，不从一个身份处理器失败后回退尝试另一个身份。只在正确范围验证对应 Cookie。一个浏览器同时登录内部端和人才端是允许场景：忽略无关命名空间 Cookie，但不能用内部 Cookie 替代人才认证，不能用客户 Cookie 替代内部认证。

workspaceId 从服务器安装配置、有效邀请或已认证会话解析，不能直接信任请求正文或查询参数中的 workspaceId。

人才 Cookie 使用独立名称、HttpOnly、Secure、host-only 和显式 SameSite=Lax。首版可固定为 `once_talent_session; Path=/api/v1/portal`、`once_talent_pre; Path=/api/v1/portal`、`once_casting_session; Path=/api/v1/casting`、`once_casting_pre; Path=/api/v1/casting`；内部现有 Cookie 不变。Path 不匹配前端页面不是问题，前端通过相应 API 获取状态；注销必须使用相同 Path/Domain 语义清 Cookie。采用这些窄 Path 名称时不要加要求 Path=/ 的 `__Host-` 前缀。[S03][S05]

同 Origin 的不同路径与不同 Cookie 只实现凭证分流，**不是浏览器脚本隔离边界**。门户、客户页所有用户文本都按纯文本转义，禁止任意 HTML/SVG/脚本、危险链接协议及将 PDF 作为同源可执行页面嵌入；附件使用明确下载和 sandbox/no-script 策略。只加载自己控制的静态 JS，无第三方埋点。CSP 不使用 unsafe-inline/unsafe-eval。上线前必须把同源 XSS 会影响内部登录的残余风险写入 ADR；无法满足这些约束则改为独立 Origin 后再开放，不用 Cookie Path 声称已隔离。[S05]

秘密认证头和同一入口有效会话不得混用；未知 `/api/*` 不能回退返回任意 SPA HTML。新增深链路由、CSP、媒体 CSP、构建路径必须有服务器测试。

## 10. 媒体链路的必要改造

### 10.1 不能只加一个上传按钮

当前绑定人才的媒体在创建、接收、完成、读取和列表阶段都校验“与人物主来源相同”，上传操作者是 Membership。TD2 集合图对独立来源的可读性判断与媒体 HTTP 的主来源限制并不完全一样。（证据 E10、E11、E14，见附录 A）

新增媒体归属必须表达：文件来自谁、提交到哪个 Person／Submission、依据哪个来源或待审核暂存上下文、谁能读、是否技术处理完成、是否业务审核通过。文件“归属”不是对素材版权的自动法律认定。

### 10.2 推荐实施方式

扩展现有上传/素材元数据的操作者与暂存归属，保留 provider、hash、worker、lease 和真实物理清理；不要另建公开桶上传服务。

`UploadContext` 为判别联合：INTERNAL_SOURCE、TALENT_SUBMISSION、AGENT_SUBMISSION。INTERNAL_SOURCE 保留已有入口的人员/来源权限；TALENT_SUBMISSION 检查真实 account 和两种业务分支：已绑定者具有目标 Person 的有效 grant；尚未绑定者拥有有效 ENROLL 申请和其 Submission。后者 personId 可以为空，仅能上传/读取自己新材料，不得选择既有素材 ID。AGENT_SUBMISSION 则检查当前 ServicePrincipal、机器负责人的有效性、机器 scope 和本次提交所属。

暂存 sourceId 可以为空，但必须有 submissionId、真实 uploader、服务器分配的审核 scope 与可验证来源描述；不能使用虚假 Source ID 或借用员工身份满足现有外键。技术状态 READY 不等于正式使用状态。采用独立 `usageState=STAGED/ADOPTED/RETIRED`（或等价有类型结构）约束 sourceId：ADOPTED 必须有已批准的来源；STAGED 不能出现在通用媒体/目录/客户接口。

审核前先停止给冻结 Submission 新增上传；选入计划的素材必须技术 READY。审核批准在同一事务内写 Source、正式归属、精确素材/集合/Work 关系和保护版本；失败保持 STAGED。immutable hash、源字节和真实 uploader 不改写。若未来跨批次引用同一资产，必须有显式合法关系，不能把 asset.sourceId 反复重指向不同来源。

引入显式 Person/Role 与媒体的关联，使独立来源合法共存。用同人关联＋相关角色/用途＋来源和授权取代 `asset.sourceId===person.sourceId`；不能仅删除旧判断。

必须逐路径改造 `Media.create/context/workerActor/claim/lease/heartbeat/finish/assetFor/listAssets/preview`、provider、HTTP、TD2 图、作品读取、候选、导出、删除及恢复。已核查现有 workerActor 确实从 `u.actorId` 查 Membership，现有 finish 直接复制 source/scope/person 成为 READY Asset；因此只改外部 HTTP 认证会在后台处理阶段失败。[E10][E26]

暂存专用读可以看本人文件，普通 assetFor 只能看获准正式文件；待审文件只能给真正有权的审核人展示。A 发布前必须经过真实异步 worker 与 PostgreSQL，而不是只测同步 MemoryStore 创建。

### 10.3 技术状态与业务状态正交

`READY` 只表示文件已通过该类型技术处理，不表示有客户展示许可。提交状态、来源确认与展示许可必须独立判断。

本人可以读自己尚在草稿／待审状态的素材；这条专用自助读策略不能复用成全体内部或客户的放行规则。人员进入删除保护时，本人端也不能继续下载被保护原件。

移出集合不删除文件；撤回客户展示立即使后续访问失效；真正物理删除仍经过依赖评估。共享 Work 使用的原件不能被一个人才通过“删除我的照片”无条件全库销毁。

### 10.4 文件格式与大小

基线 MIME 为 JPEG、PNG、WebP、PDF、MP4；单文件上限分别是图片 30,000,000 字节、PDF 50,000,000 字节、视频 200,000,000 字节。它们是当前代码参数，不是行业推荐值。[E13]

A 默认支持这些已存在的格式，不谎称支持 HEIC／MOV。手机选择不支持的格式时明确说明如何导出 JPEG／MP4；未来新增格式必须验证真实运行镜像的解码能力，不能只修改扩展名白名单。

PDF 维持“仅附件，不解析／不 OCR”的既有范围。需要模卡封面时上传者另选一张图片，或由外部 Agent 提交封面；不得为了缩略图私自加入服务端 PDF 解析链。客户原 PDF 下载需单独许可，不能默认开放。

扩展名、客户端 MIME 与文件内容不能相互替代；按格式验证、受限处理、随机对象 key、禁止任意路径与过量请求。不得把私人资料交给公共扫描服务而不说明外送。[S04]

### 10.5 真正的视频播放

新增按用途授权的播放入口，不使用内部导出链接，不把“有 MP4 封面”写成可播放。内部可在权限范围内播放原件；客户和公开播放只能使用 15.2 批准的精确素材/版本，原件恰好满足展示要求时也必须记录批准。

基线 `CosMediaProvider.readOriginal()` 通过 download 获取全文件、拼 Buffer 后验证 hash；不能每次播放器请求一个字节段就重复下载整段 200MB 文件。这一事实已核对源码。[E27]

选定新增 provider 合同 `statImmutableObject()` 与 `openByteStream({objectRef,start,endInclusive,signal})`，本地和 COS 分别实现；显式上界、固定对象身份、长度核验、背压、取消及远端忽略 Range 时的处理。HTTP 层只接受已授权资产引用，不接受调用方提供 COS key。不得在持有 PG 事务锁时等待对象存储或发送文件。

首版支持一个 byte-range，正常无 Range 为 200、有满足范围为 206，范围不可满足为 416；准确返回 Content-Range、Content-Length、Accept-Ranges、video/mp4，支持浏览器常见的开放/后缀范围。多范围请求首版按 RFC 允许的忽略方式返回完整 200 流，不伪造 multipart/206；再限制连接数、字节预算及请求频率，防止大量重叠范围导致放大。HEAD 如实现，同样先鉴权。协议语义见 RFC 9110，第 14、15.3.7、15.5.17 节。[S06]

授权流程为：短事务检查账号/recipient、角色/条目、SourceUseBasis、DisplayPermission、素材对象身份及 epoch → 打开有界流并检查远端头 → 首字节前再次短事务核对保护状态 → 发送。两个检查之间变化则中止，不先发出 body 再报错。后续 Range 请求重新鉴权；流式连接使用取消信号和限时，不承诺追回已经发出的字节。撤回策略必须说明对已开始连接的终止方式或最大剩余暴露窗口。

切片读取不等于验证了全文件 SHA256。全量 hash 在原件接收/封存时核验，播放依赖不可覆盖的 objectRef、存储对象身份、长度和技术通过状态；不得拿一个片段与全文件 hash 比较后声称通过。检测到存储不一致则隔离并阻断。

MP4 容器不保证 codec 可播。A 固定支持经实际运行镜像及 iOS/Android 验证的 H.264/AVC 视频、AAC 音频或无音频组合；不支持的编码明确拒绝/标记需转换，不偷偷当 JPEG 展示。前端页面 CSP 增加明确 `media-src 'self'`；本地文件预览需 blob 时只对所需 img/media 指令开放 blob，不开放脚本。真实手机播放、首次 seek、末尾 seek、中断与并发流是验收场景。

### 10.6 上传重试与弱网

现有上传是完整文件、有 Content-Length、有限租期，并非分片断点续传。[E11]

首版必须支持单文件失败后重新上传与部分文件成功保留；按钮和文案不能写“断点续传”却重传全文件。上传进度和状态查询与正式提交分开。

文件传输完成但响应丢失时先查当前 uploadId；已收到则继续完成，不另建第二个 Asset。提交集合和案例使用稳定客户端条目键，避免重复挂接。

未来分片上传作为独立协议扩展，包含分片授权、hash、清理和额度预留；不是给现有 PUT 加无限重试。

### 10.7 容量、并发与费用

当前限制包括单操作者同时 3 个、工作空间同时 20 个、暂存声明字节 1 GB、未清理准入声明字节 2 GB，以及上传／处理时限。（证据 E13、E10，见附录 A）

这不是“COS 容量不足”，而是应用层配额。按 talentAccount／ServicePrincipal 区分实际使用主体，防止所有人才共用一个员工额度，也防止单人占满所有容量。

新增可配置 workspace 存储预算、单人才预算、并发与每小时创建限制；元数据记录额度占用，物理删除确认之前不能提前释放已占用容量。所有新限额需给出默认值、超限响应、运维修改方式和测试，禁止简单设为 Infinity。

成本由真实文件数量、平均体积、访问量和保留政策计算。不得用“支持 50,000 记录”推导“可承载 50,000 个完整模特”。

### 10.8 草稿素材的保留、回收和容量归还

基线 expire/清理只选择 FAILED/CANCELLED 且未生成 Asset 的上传；READY 为终态，purgeAllowed/markPurged 也禁止有 Asset 的情况。外部草稿中新生成的 READY 文件不会因此自动释放。不能简单延用这套清理器，也不能把技术成功改成 FAILED 来钻清理条件。[E10]

首版新增**暂存业务回收计划**，复用现有物理清理和安全日志，不另造公开文件删除接口：

| 暂存情形 | 产品默认保留策略 |
|---|---|
| 从未提交的 DRAFT | 最后一次有效保存后 90 天；到期前 7 天提示；名额过期只暂停继续提交，不立即删除内容 |
| SUBMITTED 尚未决定 | 最多 180 天并提示内部审核；到期转 EXPIRED，不自动批准 |
| REJECTED / PARTIALLY_APPROVED 未采纳项 | 最终决定后 30 天，允许复制新草稿；只清未采纳且未被合法引用的素材 |
| WITHDRAWN / 主动放弃 | 7 天短暂保留或本人明确立即申请清理；不影响原正式资料 |
| 已 ADOPTED 或被新有效草稿引用 | 不按原草稿 TTL 删除；按实际正式/暂存依赖和删除计划处理 |

以上为明确产品默认值，不是法定保留期限，须在表单和运维配置中展示；不会用清理任务改变已有合同中的独立保留义务。通知没有成功送达也不能宣称已通知；使用页面到期提示作为基础。

回收顺序：事务内检查 expiry/owner/当前依赖→标记 RETIRED 并递增保护版本、禁止新挂接→记录回收计划与写前安全日志→事务外删除已知私有对象→确认本地和 COS 结果→将 Asset 置 ERASED、清理敏感元数据并记录 purgedAt。并发批准、fork 引用和回收采用同一资源版本/锁；先被合法采纳则取消暂存回收，先退休则批准必须拒绝并要求重新上传。

删除失败或结果未知不释放预算、不虚报删除。正式依赖、客户安全副本及原件共享都要计入检查；清掉申请不等于清掉已采纳的模特作品。配额统计使用实际预留/占用/确认清理记录，避免上传、采纳、衍生三处重复收费或漏算。

## 11. 外部 Agent 摄取合同

### 11.1 能力边界

外部 Agent 负责从用户授权提供的微信笔记、模卡、图片、视频说明等提取信息；ONCE OS 负责结构、权限、存储、来源、冲突与使用资格。

首版以明确 API＋机器使用说明交付；MCP 是可选适配层，不是验收前提。使用现有 ServicePrincipal；新增操作逐一加入外层和 TD2／摄取授权白名单，不开放整个后台。

### 11.2 新增最小动作

读取版本化摄取 schema／受限字典；创建摄取 submission；添加结构化条目；获取上传意图并上传允许文件；校验并提交；读取自己提交的处理状态。

Agent 默认不能：确认来源用途、批准本人认领、核验成年／资质、查底价、读取全库照片、直接发布官网或客户链接、删除不属于本次草稿的媒体。

已有 `talent.fact.write` 的旧机器行为保留合同测试；新的导入链优先提交草稿与提议。禁止在没有迁移方案时悄悄改变旧权限语义，也禁止因旧机器可 patch 就让新 Agent 覆盖全部确认资料。

### 11.4 去重与幂等

`externalSubmissionKey` 只在 workspace＋ServicePrincipal 范围内唯一；不作为跨供应商的人物身份。

已有 verified ExternalRef 可以提供精确匹配线索；它不等于本人账号的认证绑定。同名、同照片或同经纪人电话只能提示潜在重复，不自动合并。

新人物摄取先产生待确认记录，后台明确创建或关联目标。客户端 stable item key 贯穿上传、集合、案例，失败重跑只补缺失部分。大批量按有状态小批处理，不能一个 HTTP 请求运行几百次数据库写入。

### 11.5 来源不由 Agent 自行“批准”

Agent 可以申报来源、提交引用与原始材料，但 source 内容、网页文本或笔记里的指令都属于不可信业务数据，不能改变系统权限或提示 Agent 使用更高权限令牌。

不要在 OS 内接受任意 URL 并代为下载。首版让 Agent 上传已取得的字节；外部作品链接只是展示引用，不进行服务端抓取，避免引入额外抓取和网络访问边界。

## 12. 查询模型与筛选语义

### 12.1 一个正常入口，一个查询合同

新增 TalentDirectoryQuery，人才目录和候选中的“找人”共用组件和字段语义；旧接口仅保留明确兼容用途，不再作为三套正常入口。

主查询固定为 `POST /api/v1/directory/talents/search`，属于应用层 READ，不创建业务命令回执、不要求 Idempotency-Key，但仍需要内部会话、精确 Origin、CSRF、严格 JSON 校验和只读结果。筛选、分页、排序在 body 中，禁止记录完整搜索正文。新 route mode/schema 及 transport 要支持 POST READ，不强迫沿用原来 GET 拼 query 的 read helper。

不再新增另一套含价格条件的 GET 目录接口；旧 GET person.list/td2.person.list 保持旧合同。新列表和详情按当前权限生成数据；过滤和 facet 本身同样要鉴权，见 9.4。公开客户端没有全库搜索。

### 12.2 过滤条件的明确规则

| 条件 | 语义 |
|---|---|
| 同一维度多选 | OR，例如深圳或广州 |
| 不同维度 | AND，例如女模且专业且身高满足 |
| 职业专属资料 | 必须属于此次选中的 PersonRole |
| 素人／专业 | 使用 ModelProfile，不借用通用语言等级 |
| 国模／外模 | castingMarketCode；国籍另筛 |
| 年龄 | 指定日期计算，区分精确、区间和未知 |
| 身高／三围 | 只用有效当前量尺；缺失不当作 0 |
| 作品行业＋类型＋角色 | 同一件作品上的对应署名同时满足，不能拿三个不同案例拼结果 |
| 可接拍类型 | 当前意愿声明，不能用作品内容替代 |
| 有合作经历 | 明确选择外部案例或 ONCE ACTUAL 合作，不能混为一个认证标识 |
| 档期可用 | 当前有效时间声明覆盖查询区间；未知不匹配“确定可用” |
| 报价范围 | 币种、单位、时长口径一致再比较 |
| 标签 | 使用有效字典与可用 assignment；不能通过标签绕过来源条件 |

### 12.3 Facet 计数

首版定义为：应用其他维度条件后，对当前维度枚举可见的唯一 Person 数量。一个人有多个角色、多个作品也只计一次。当前选中项即使计数为零，也应保留以便取消。

总数、选项数、列表、导出候选人数使用相同可见性规则。不允许先做全库统计再过滤显示。

### 12.4 查询实现

新增有类型的 `Tx.talentDirectoryQuery()`，在 PrismaStore 以参数化查询进行数据库筛选、同对象 EXISTS 条件、去重和分页。将 `loadTalentGraph` 保留为受限规模下的语义参考与差异测试基准，不让每个外部请求都加载全工作空间图。

参考图不是无限扩展性能方案；不能删掉 50,000 上限后声称完成优化。SQL 路径必须通过与内存语义一致的测试，覆盖来源、字段依据、角色、撤回、归档、合并以及媒体可见性。

初期保持现有短事务与授权一致性边界，不同时重构全局数据库锁。对该锁造成的并发限制进行测量，达到门槛后再用单独 ADR 处理查询隔离；不能为性能在同一 PR 中删除授权敏感事务锁。（证据 E14、E16，见附录 A）

### 12.6 保存视图与批量选择

新 SavedTalentView（或同等已有资源）只保存 schemaVersion、筛选和排序，不保存查询结果快照。默认 owner-only；含客户需求、姓名关键词、价格或敏感筛选时存服务器且不写 URL、sessionStorage、localStorage。共享内部视图必须重新检查接收人是否有权执行全部条件，不能通过分享条件泄露成本阈值。

URL 可以保留不带个人数据的页面标签、分页、布局及随机 viewId；viewId 不能作为可免认证访问的凭证。跨刷新恢复有选择地从服务器读取；若查询仅在内存中且用户刷新，应明确恢复为空，不能承诺不存在的持久化。前后端日志、错误跟踪和代理日志一并屏蔽敏感查询正文。

候选勾选保存 Person＋Role 上下文，翻页不丢失；创建候选前服务端重查每项可用性和角色。失效项报告为失败，不能“已成功加入 N 人”却缺项。批量全部成功时可原子提交；允许部分成功时必须返回逐条有回执的状态并显示，不能静默跳过。

## 13. 作品案例与媒体集合如何协作

集合用于组织资料；Work 用于表达有具体身份和署名的案例。两者都需要，但不能要求用户理解它们的底层区别。

“我的模卡／素颜照／视频介绍”对应 MediaCollection；“品牌 A 广告拍摄”经审核对应 EXTERNAL Work、WorkCredit、WorkAsset 和新增 WorkMetadata。一个真实案例只用一个 Work，不把每张照片建成一件作品。

没有明确项目名称、品牌或年份的作品照片可以放入普通 PORTFOLIO 集合，不强制填写虚构品牌、日期或客户。案例也允许年份和品牌未知。

已有 Work 被多人共用时，本人只能提交自己的署名声明或修改建议，不得通过个人表单直接改其他人的信息。两个同品牌同标题案例不自动合并，工作人员确认后复用同一 Work。

外部案例不产生 ProjectParticipant.ACTUAL；ONCE 项目的实际合作标识继续由内部项目流程决定。客户看到“本人提供的案例”与“ONCE 合作项目”可以分开说明，不能在没有依据时显示官方背书。

### 13.1 候选精选素材需要扩展

基线不仅 ShortlistItemAsset 带 workId；数据库 `shortlistItemAssets_itemRef_fkey` 还把 `(workspaceId,itemId,workId)` 绑定到父候选的同一个 workId，addItem 的去重也使用 Person＋Work＋Role。因此只给素材子表增加 collectionItemId 不足以支持“一个模特＋多个案例”。[E05][E28]

**本版选择：新体验层以一个 Person＋PersonRole 为一个候选行。** ShortlistItem 的旧 workId 仅保留为 `legacyPrimaryWork` 兼容信息，不再限制新精选列表的所有 Work。不复制一份新的候选系统。

新增或扩展两种严格引用：`WORK_ASSET` 带 workId/workAssetId/assetId；`PERSON_COLLECTION_ITEM` 带 collectionId/collectionItemId/assetId。以带 kind 的 CHECK 保证二选一，保留 workspace 与真实 workAsset/collectionItem 外键，新增或调整父 item 的 FK，使它绑定 itemId 而不错误要求所有子项的 workId 等于父 workId。服务层仍核对每件 Work 有当前 Person 的当前 Role 署名，集合属于该人且角色通用或匹配。不能用放松 FK 掩盖同人/同职业检查。

迁移只追加：保留旧 item、asset link ID 与顺序，旧 workId 和相应版本记录原样保留；旧数据可能已有同人同角色多个 Work 的多行候选，标记 LEGACY，不强行加全局唯一索引导致升级失败，也不静默合并员工备注。新行标记 PERSON_ROLE_V1 并对 `(workspaceId,shortlistId,personId,personRoleId)` 建约束；面对已有 legacy 行，先由员工明确“归并为一位候选/保留分行展示”的迁移操作决定，并保留来源映射。

旧 addItem/roleReview/remove/reorder、Work unlink、集合移出、人员合并、来源删除、候选导出重建和展示生成都要接收新关系分支。旧客户端不能无视新集合关联后覆盖整行；按版本适配或明确要求升级。禁止把旧有 WORK_REQUIRED 检查整体删掉而任意挂 assetId。

新候选默认最多 100 行、每行精选 12 项媒体，可含模卡、不同案例、介绍视频；素材标题和案例署名从各自依据生成。客户版还需独立用途许可和媒体内容审核，不因内部能加入候选就自动对外可读。

## 14. 参考报价与可用时间：足够用，不扩成财务和排期系统

### 14.1 三个不同口径

| 口径 | 归属 | 谁维护 | 谁能看 |
|---|---|---|---|
| 人才参考价 | 某人某职业及服务条件 | 本人提交、内部审核 | 本人及有权内部人员 |
| ONCE 内部议价／采购参考 | 某人某职业或某次需求 | 有权内部人员 | 具备独立成本权限的内部人员 |
| 某次客户报价 | 某候选／项目／分享版本 | 有权内部人员 | 内部及明确启用价格展示的对应客户 |

不能简单将自报价复制一份叫“内部成本”，之后让两份数值无来源地漂移。内部议价可以引用原 TalentRate 并记录本次约定差异；客户价使用独立 `CastingQuoteLine`，不返回计算成本和利润。

自报价并非最终报价；参考价和客户价都不代表锁档。客户分享默认不展示价格，员工显式选择后才输出对应客户价。

### 14.2 最小价格字段

`personRoleId`、价格类型、`amountMinor`（整数最小货币单位）、currency、unit（HOUR/HALF_DAY/DAY/PROJECT）、includedHours 可空、minimumUnits 可空、条件说明、适用拍摄类型、validFrom、validUntil、sourceId。

“半天”或“一天”必须能注明包含时长；交通、妆造、超时、使用范围等未约定时显示待确认，不自动包含。零值必须是明确的免费声明，未知用 null 或无记录。

不同币种、单位或服务条件不能混在同一个数字范围筛选；不引入自动汇率估算。对客户已发出的价格变更需要新版本，不被本人参考价更新偷偷改变。

### 14.3 基础可用时间

只做时间区间声明：`AVAILABLE / UNAVAILABLE / ASK`，带 personRoleId、时区、声明时间、核对时间和来源。不做订单、占位、押金和正式锁档。

内部存 UTC 区间，采用 `[start, end)`，前端使用明确业务时区；日期型输入按该时区转换，不拿服务器时区隐式解释；全天记录按当地日历的下一天结束，不能总用 start+24h 处理夏令时。覆盖整个查询区间且没有冲突、来源仍有效，才能匹配“声明可用”。

同一人同一职业的重叠有效声明默认 UNAVAILABLE 优先；该不可用声明在其明确有效期内不因“30 天未更新”自动失效，除非被本人显式撤回/替代。跨角色的时间冲突不能因为摄影／模特是两个身份就认定可同时出勤。有冲突时展示“需确认”，不假装调度系统已经解决冲突。

缺少记录或声明过旧时显示 ASK。可用信息新鲜度阈值是可配置产品参数，应在 UI 显示上次更新时间，不作为真实预订保证。

## 15. 客户分享、精选版本与展示许可

### 15.1 三级展示不是三个互斥档位

内部可用不等于可发客户，客户可看不等于官网公开，官网可看不等于开放原件/电话/内部价格。用途分别为 INTERNAL_DIRECTORY、CLIENT_CASTING、PUBLIC_WEBSITE，不用一个 visibility/isPublic 代替。

明确三层不同决定：TalentConsent 记录本人/获准代管人的真实同意；SourceUseBasis 证明具体来源内容在特定用途可用；DisplayPermission 是 ONCE 对精确字段/素材/场景的对外批准。后者不能由员工凭空制造前两层的授权依据，也不因“本人上传了照片”就推定第三方摄影师、客户品牌或其他出镜人的全部权利已经取得。

授权核对记录实际授权方、适用内容、用途、期限、文本版本/证明，不要求搭一套法律规则引擎；无法确认必要展示依据的素材不对外发。代管权与公开授权权逐项授予；监护/经纪关系成立不能自动获得所有用途权力。外部 Agent 的来源说明是待核对信息，不是许可。

原 UsePermission(INTERNAL_EXPORT) 只用于原有内部导出；它不替代 DisplayPermission。读取时以 7.3 的统一用途判定及当前有效展示许可共同检查；撤回、过期不能只阻止新分享而允许旧链接继续访问。[E15]

### 15.2 分享生成

创建 CastingShare 必须有有权访问的内部清单和指定用途；先批准不可变 Version/Entry 白名单 payload，再签发秘密。payload 只含允许的艺名、职业、量尺/年龄显示、精选案例简介、媒体引用和显式启用的客户价；禁止 serialize 内部 Shortlist 或 Source。

**对外媒体审核是正式合同，不只是 UI 提醒。** 每个被选媒体生成 DisplayMediaSelection，关联 exact assetId/renditionId、完整 hash、尺寸/时长、用途、原件及衍生关系、审核人、reviewRevision、决定及依赖。上传者/Agent 提交的 sanitized/safe 布尔值没有批准效力。审核预览必须对应最终要发送的同一字节版本，更新文件或裁切必须重新审核。

检查对象包括图片中的电话/微信/二维码、水印与客户保密信息，PDF 全部拟提供内容，视频画面/字幕/声音和所有被展示出镜信息；只看封面或 JSON 脱敏不算完成。内部审核后的正常原图可以直接作为批准的展示版本，不强制每张图都复制/加工；含敏感内容则由用户、内部编辑或外部 Agent 提交安全衍生文件，本系统不因此增加 PDF OCR、自动视频审核或在线剪辑功能。

衍生素材必须显式关联原件/原用途依据，原件保留不被覆盖。分享使用已经批准的 rendition，而不是前端 CSS 遮盖原图后仍把原始字节发给客户。原来源或相应许可撤回时，衍生副本也失效；不能因为衍生文件有新的 assetId 就逃过依赖检查。不存在合格版本时，阻止该项分享而非自动退回原件。

分享中使用不透明 mediaRef 和清洁文件名，缩略图、播放、下载使用同一审批链。PDF 原件下载默认关闭，只有明确审阅内容并取得原件用途许可才提供；按钮只显示模卡图片不自动开放背后的 PDF。多素材生成失败时保留 DRAFT Version，不发布一半条目或用占位 URL 伪装通过。

### 15.3 内容冻结与权限实时失效

冻结的是展示内容，不是访问资格。DisplayDependency 对每个字段/素材至少保存：subject/fieldPath、frozenValueDigest、被审核的不可变依据版本或提交决定 ID、所需用途、permissionId/revision、源/资源保护 epoch、期限、素材 bytes/hash/对象身份及原件衍生链。没有可长期核对的不可变依据，就不能生成承诺可冻结的 Version。

读取当前分享时依次检查：share/version 仍可访问；recipient 会话有效；相关人物/素材未被删除保护、隔离或合并失效；当前用途依据仍允许这份冻结内容；来源和展示许可未撤回/到期；实际文件仍是被批准的对象。**不能以当前 Person 字段值的 digest 去证明旧快照内容**；普通字段已改，旧快照用其自身冻结值和当时合法依据核对。

| 变化 | 已发版本行为 |
|---|---|
| 普通艺名/简介/本人参考价变更 | 保持原内容；员工主动生成新版本；旧报价不被改 |
| 原来源修改普通说明但仍能证明被冻结依据合法 | 保持展示，不仅凭普通 revision 改变就全部关闭 |
| 来源撤回、用途范围收窄、到期、证据删除/脱敏或重大安全纠错 | 阻断相应条目/媒体；无法精确判定影响则关闭相关版本重新核对 |
| Person/Role/Work 归档 | 不再新增候选；首版关闭包含其活跃展示的条目，内部历史保留；这仍不等于撤回全部独立来源 |
| Person 合并、维护归属争议或未成年人用途冲突 | 外部版本不自动跳到主档/新账号；暂停受影响用途并重新确认 |
| 恢复旧数据库或权限检查失败 | 全部旧外部凭证失效；禁止使用缓存 snapshot 兜底 |

内部 scope 的改变至少递增保护 epoch 并触发对依赖的重查。由于外部客户不是 scope 成员，不能简单复制内部 scopeVisible；新范围若影响已批准对外展示资格，必须关闭它，无法证明无影响时默认关闭。旧 link 不能成为范围收窄的后门。

被阻断的条目返回不含姓名/原照片的“内容已不可用”占位，或按策略整体 SHARE_UNAVAILABLE；不要在错误中泄露撤回原因、内部来源和其他候选。历史快照 payload 仍受授权及删除规则，不是永久留存全部隐私的理由。

### 15.4 分享链接和访问主体

首版默认“持有链接可查看”，可附访问码，短期有效且可撤回。界面明确：链接可能被转发，不能声称只被指定姓名的客户看到。需要真正限定接收人时使用经验证邮箱的受限分享模式，不用输入一个客户姓名假装完成身份认证。

分享令牌交换为独立客户会话，后续不把 bearer token 挂在图片 URL 上。增加 share 内稳定 `CastingRecipient`，Session 只负责可过期/轮换的凭证；反馈和回执 principal 使用 recipientId，不用 sessionId。匿名 recipient 只是一个浏览器访问身份，不等于经核验的自然人。

一个浏览器可打开多个分享：`CastingRecipient` 归属于一份 share，`CastingSession` 是浏览器凭证，两者不设永久一对一。使用 `CastingSessionAccess(sessionId, shareId, versionId, recipientId, grantEpoch)` 建立明确的访问映射；同一 session 对一份 share 只能对应一个 recipient，并允许该 share 的多个已批准 version。数据库复合外键保证 recipient 属于同一 workspace/share，每条请求从实际 session 与路由 share/version 解析该映射，不接受正文指定的任意 recipient。打开 B 只追加 B 的访问，不替换 A；`X-ONCE-Casting-Recipient` 必须与本次路由解析出的 recipient 相符。初版链接固定到一个 version，发布新版本显式轮换/另发链接，旧版状态明确展示，不静默把旧反馈应用于新版。持有旧链接仍须符合旧版当前状态和权限。

凭证轮换在可证明原 recipient 身份时保留同 recipientId；丢失全部匿名 Cookie 后只能建立新的匿名 recipient，不声称自动找回“同一客户”，UI 允许显示多访问者反馈。不凭昵称/姓名合并匿名访客。只有获准 shareVersion 和 entry 才能读对应媒体，禁止全库人物查询。

默认分享有效期 7 天、最多继承内部清单 100 人上限；可缩小，扩容须有容量测试。每个客户条目建议首版最多精选 12 项媒体，超过时需明确选择，不自动把整个人才相册发出去。

### 15.5 客户反馈

反馈为 `INTERESTED / NOT_INTERESTED / UNDECIDED`＋可选文字。使用 shareVersionId、entryId、recipientId 作为稳定归属，审计另记录 sessionId；匿名访客只代表该访问身份，不声称已确认客户本人。偏好更新有自己的 revision，两个标签修改同一偏好不得静默最后写入覆盖。

分享版本变更后旧版反馈保留但不自动搬到新人物或新报价；UI 明确版本。反馈写入继续幂等、校验条目属于此版本、校验分享未过期／撤回，限制文字长度及提交频率。

未确认档期时，任何按钮不得写“已预订”。导入反馈不能设置 ProjectParticipant.CONFIRMED 或 ACTUAL。

### 15.6 公开官网发布

Release C 使用 PUBLIC_WEBSITE 独立授权＋人工批准，生成专门 PublicTalentProjection，再交给官网。本人门户和内部目录不直接作为公开数据接口。

发布接口对新增、更新、撤回带稳定外部资源键和版本；任务可重试且不重复创建官网页面。发布回执、失败、删除／撤回确认都需记录。

初期只构建确定的 ONCE 官网适配，不建设通用多 CMS 插件平台。真实 CMS API 未核对前，不在文档中虚构 API 路径。若适配尚未完成，状态必须为 C 未完成，而不是生成一个空 public 路由算交付。

撤回先关闭 OS 侧公开读取，再发送官网下架任务；官网同步失败保留明确未完成状态并提醒内部处理。缓存、第三方搜索结果和已下载副本无法保证瞬间撤回，不得承诺完全抹除互联网副本。

## 16. 必须同步覆盖的生命周期

### 16.1 删除与撤回

人物进入删除保护，立即拒绝新的认领、本人修改、上传完成、Agent 关联、客户读取和新增分享。原有删除影响预览必须枚举新增引用。

影响范围至少包括：维护 grant、未完成 invitation／claim、草稿／提交 payload、本人身份关联、量尺和新字段、标签、作品描述、媒体关系、价格、可用时间、分享快照、反馈、公开投影、展示许可和消息发送记录。

**不能把“审计不可改”解释为必须永久保留敏感 payload。** 延续现有受控历史脱敏／销毁策略，审计保留必要的操作事实，内容按冻结的删除计划处理。

### 16.2 账号注销与人物删除不是一回事

账号停止维护可以撤销 grant 和会话，但不自动消灭独立来源支持的全部业务档案。用户申请删除人物资料则进入专门的删除影响流程；系统说明会处理哪些对象，不能用“账号注销成功”暗示所有素材已物理删除。

一个监护账号注销不会无条件删除其他独立授权主体的资料；每个 Person 分别评估。

### 16.3 人物合并

合并前检查双方的有效维护绑定。只有一边已认领时，可在人工确认后迁移对应 grant；两边绑定不同账号时必须暂停自动合并并解决身份冲突，不能让一个账号因此获得另一个人的资料。

未使用邀请默认撤销并重签，不自动把原链接指向新目标。共享版本和外部条目 ID 不静默重定向；需要重新核对许可和内容。旧 Person alias 的内部只读处理继续保留，不作为外部授权捷径。

合并还要处理 ModelProfile、Demographics、标签、量尺指针、WorkCredit、媒体关联、报价和可用时间冲突。主档选定不等于所有字段直接取主档覆盖。

### 16.4 导出、重建和数据库备份

授权的业务数据导出应包含本次新增的正式人才事实、允许迁移的关联及必要来源／许可记录；不能只导出旧 Person 字段，导致新系统“能用但搬不走”。

OTP、会话、原始 token、活跃分享秘密、账户恢复凭证不进入普通业务 JSON。新环境重建不能继续信任旧环境的登录会话和认领凭证。内部备份可以含加密字段，但受独立密钥、访问控制及恢复隔离保护。

JSON 导出／重建版本必须提升并提供当前基线升级合同；不强制兼容任意历史开发包。已应用的数据库迁移不得改写，不执行破坏性 reset。

### 16.5 灾难恢复

新会话、邀请、分享和待发送消息全部绑定 recoveryEpoch。恢复时旧的外部有效凭证失效，未完成的短信／邮件不盲目再次发送，未完成上传按真实状态核对，旧 PUBLIC 发布状态不能在隔离状态下自动恢复外送。

人才可以在恢复结束后通过正常认证重新登录；维护关系的恢复需要验证其当前有效状态。客户链接由内部明确重签，不凭恢复的历史 token 继续放行。

所有外部入口都要服从维护／恢复隔离开关。不能只让 `/health/ready` 返回 isolated，公开素材路由却仍然可以读取。

## 17. 拟新增 API 合同与现有接入点

以下是建议实施的路由合同，**基线不存在这些路由**。所有普通写入使用 JSON 严格校验、Idempotency-Key、当前身份绑定与适当 expectedRevision；认证与 SECRET 操作另按专用语义处理。

### 17.1 路由分组

| 入口 | 方法与路径（拟新增） | 核心约束 |
|---|---|---|
| 目录搜索 | `POST /api/v1/directory/talents/search` | READ＋严格 body、Origin/CSRF；不生成回执，禁止记录敏感条件；统一 facets |
| 主详情 | `GET /api/v1/directory/talents/{id}` | 内部 DTO，不返回超权字段 |
| 快速建档 | `POST /api/v1/directory/talents` | 人物＋人才＋所选职业一次事务；需要真实来源上下文 |
| 邀请记录 | `POST /api/v1/talent-invitations` | 创建 DRAFT，不返回秘密 |
| 签发／轮换 | `POST /api/v1/talent-invitations/{id}/issue` | SECRET，hash 存储，结果未知可撤销重签 |
| 撤销邀请 | `POST /api/v1/talent-invitations/{id}/revoke` | 当前状态检查，旧凭证失效 |
| 认证挑战 | `POST /api/v1/portal/auth/challenges` | 统一提示、发送频控、明确用途 |
| 验证登录 | `POST /api/v1/portal/auth/verify` | 限次、限时、一次使用、独立 Cookie |
| 预认证初始化 | `POST /api/v1/portal/auth/context` | 精确 Origin＋自定义头，设置预认证 Cookie，返回 CSRF/contextId；不复用内部 pre-auth |
| 本人会话 | `GET /api/v1/portal/me` | 当前账号/CSRF/自己的 grant 与申请概要；不返回其他人 |
| 退出 | `POST /api/v1/portal/auth/logout` | Origin/CSRF，服务端失效 session，按原 Path 清 Cookie，不重放业务写入 |
| 本人申请 | `GET /api/v1/portal/claims`、`POST /api/v1/portal/claims/{id}/renew-admission` | 只读自己申请；续办需有效 ENROLL 上下文和名额 |
| 邀请检查 | `POST /api/v1/portal/invitations/inspect` | 不消费、不返回内部完整档案 |
| 认领申请 | `POST /api/v1/portal/claims` | 认证／目标匹配／人工待审分支 |
| 认领审批 | `POST /api/v1/talent-claims/{id}/decide` | 内部权限，审计，绑定原子性 |
| 自助详情 | `GET /api/v1/portal/profiles/{id}` | 逐人 grant＋字段白名单 |
| 草稿创建／保存 | `POST /api/v1/portal/submissions`、`PATCH /api/v1/portal/submissions/{id}` | grant 或自有 ENROLL 申请，DRAFT CAS，服务器保存 |
| 草稿/提交读取 | `GET /api/v1/portal/submissions`、`GET .../{id}` | owner 白名单与当前暂存资格，不混入内部审批原文 |
| 撤回／重新草拟 | `POST .../submissions/{id}/withdraw`、`POST .../{id}/fork` | 状态 CAS；固定旧 payload，新建草稿及依赖，不原地重新开放提交 |
| 提交审核 | `POST /api/v1/portal/submissions/{id}/submit` | 冻结内容，逐对象基线、关系原子性 |
| 审核列表／决定 | `GET /api/v1/talent-submissions`、`POST /api/v1/talent-submissions/{id}/decide` | 内部批量审核，不伪造认证 |
| 本人上传意图 | `POST /api/v1/portal/uploads` | 属于有效 submission；已绑定需 grant，ENROLL 未绑定需自己的有效申请，不要求虚假 Person |
| 本人二进制 | `PUT /api/v1/portal/uploads/{id}/content` | 原 uploader、限额、hash、当前权限 |
| 本人完成／状态 | `POST /api/v1/portal/uploads/{id}/complete`、`GET /api/v1/portal/uploads/{id}` | 失去响应先查状态，不重复素材 |
| 上传取消／原草稿清理申请 | `POST .../uploads/{id}/cancel`、`POST .../submissions/{id}/discard` | 分别取消未完成传输与申请未采纳素材清理；不得全库删共享原件 |
| 自助媒体 | `GET /api/v1/portal/media/{id}/preview`、`.../playback` | 自助读策略；视频 Range 重查 |
| Agent schema／摄取 | `GET /api/v1/ingestion/schema`、`POST /api/v1/ingestion/submissions` | 机器限定；更新外层白名单 |
| Agent 上传／提交 | `/api/v1/ingestion/uploads/*`、`POST .../submissions/{id}/submit` | 同一机器及当前摄取上下文 |
| 分享创建／签发 | `POST /api/v1/casting-shares`、`POST .../{id}/issue` | 先批准白名单快照，再签发秘密 |
| 客户预认证初始化 | `POST /api/v1/casting/auth/context` | 精确 Origin＋自定义头；设置 casting 专属预认证 Cookie，返回 CSRF/contextId，不依赖 talent 会话 |
| 客户会话 | `GET /api/v1/casting/me`、`POST /api/v1/casting/auth/logout` | 只返回本会话有权访问的 share/version 与对应 recipient/CSRF；退出撤销本 session 的 access，不删除历史反馈 |
| 分享交换 | `POST /api/v1/casting/access/exchange` | 令牌＋访问码（启用时）、限流、Origin/预认证校验，生成 recipient/session 的精确授权 |
| 分享查看／媒体 | `GET /api/v1/casting/shares/{id}/versions/{versionId}`、`GET .../entries/{entryId}/media/{mediaId}` | 不透明引用，当前依赖重查，实际字节须与审核版本相同 |
| 内部分享撤销 | `POST /api/v1/casting-shares/{id}/revoke` | 同事务撤销版本/访问资格并增 epoch，后续字节拒绝 |
| 客户反馈 | `PUT /api/v1/casting/shares/{id}/versions/{versionId}/feedback/{entryId}` | recipient＋版本＋条目、expectedRevision、幂等；无预订效果 |
| 用途授权／撤回 | `POST /api/v1/portal/consents`、`POST .../{id}/revoke` | 本人可控制被授权用途；撤回立即阻断后续使用 |

登录退出、上传取消、列表分页、分享撤销／新版本、价格／时间维护等配套路由必须在相应 PR 的合同中补齐并生成类型；表内不是允许只做主路径、遗漏异常动作的借口。

### 17.2 命令返回

普通命令沿用 `{operationId, resourceId, revision, state, replayed}`。结果检查必须绑定具体操作允许状态；不能把任意 200 都视为成功。

认领和提交成功但响应丢失：同一身份、同键、同内容重放。重复键配不同内容返回冲突。重放仍检查当前账号、grant／scope、来源及资源可访问性。

读接口返回自助或客户投影；不要返回 `CommandReceipt` 当作业务详情。SECRET 不能套用普通回执保存原始凭证。

### 17.3 错误码及前端动作

| 错误 | 面向用户的动作 |
|---|---|
| `INVITATION_UNAVAILABLE` | 链接无效、过期或已撤销，联系 ONCE 重新邀请；不暴露目标隐私 |
| `CLAIM_REVIEW_REQUIRED` | 已提交申请，等待 ONCE 确认；不开放内部档案 |
| `IDENTITY_MISMATCH` | 使用被邀请的联系方式认证，或申请人工确认 |
| `PROFILE_ALREADY_BOUND` | 进入本人的既有资料；对非本人只显示不可认领 |
| `REVISION_CONFLICT` | 查看允许读取的变化，重新确认，不覆盖新值 |
| `SUBMISSION_NEEDS_REBASE` | 当前资料已变化，重新核对该次修改 |
| `MEDIA_FORMAT_UNSUPPORTED` | 明确支持格式，不提示“系统未知错误” |
| `MEDIA_QUOTA_EXCEEDED` | 显示本人可知限额与处理方法，不泄露其他人的用量 |
| `DISPLAY_PERMISSION_MISSING` | 仅内部显示缺许可项，阻止签发 |
| `SHARE_UNAVAILABLE` | 分享已失效，不返回旧快照或内部原因 |
| `COMMAND_OUTCOME_UNKNOWN` | 保留待核对状态，不生成新键盲重发 |
| `PROVIDER_UNAVAILABLE` | 不宣称已发送验证码；给出改用已启用渠道或稍后重试的明确入口 |

### 17.4 合同版本

新增体验层使用 `once-talent-experience-v1`。旧 TD2 schemaVersion 不在未更新校验器时接收新字段；原有严格未知字段拒绝不能取消。

新增核心事实/未知量尺日期的目标版本固定为拟实现的 `once-talent-v2.1.0`，同步 schema 路由、生成请求类型、数据库约束、新/旧投影、导出/重建。现有已测 v2.0 写入通过明确旧字段适配器保留原语义，不能悄悄接受新字段；新读结果显式标 2.1，无法表达 UNKNOWN 日期的旧消费者要求升级，不伪造日期或不告知地删除记录。

新增事实不能仅进入 Prisma 表。PR-01 为 Demographics、ModelProfile、标签 assignment 等定义有类型的 schema/源依据、字段权限、同角色关系、搜索和生命周期；选择纳入 TD2_FACTS 时必须扩展相应 OWNER_KEYS、字段证据/转移白名单及完整性检查。客户端禁止提交 internalSummary、verifiedAt、approvedBy、protectionEpoch 等系统字段。

### 17.6 首版配置数值与使用边界

这些是本次产品初始默认，不是现有代码参数、性能保证或法律期限；实现为有类型配置并可收紧。扩大预算需内部批准，不能由 Talent/Agent 改 env。

| 配置 | 首版默认／规则 |

| 反馈 | 文本最多 1,000 字符、同 recipient 30 次/分钟；权限/状态在每次写入重查 |

具体配置变量名可由实现确定，但必须在 PR-00/相关合同中逐一映射，不允许同一阈值在两处 env 各用不同含义。验证码发送预算并非能推导费用为零；供应商实际计费未知时报告 UNKNOWN。

**验收：** 原 Person ID 不变，旧作品保留；本人不进入 Membership；另一账号无法读写；重复扫码、双人竞争、响应丢失、账号切换可正确处理；本人提交后在后台同档看到待审变化。

### PR-03｜多来源媒体、模卡、案例、视频和完整维护旅程

**交付：** 本人／Agent 暂存媒体上下文，来源与媒体关联改造，行内上传、排序、封面、案例表单、MP4 播放、格式提示、配额配置、草稿清理和撤权检查。

审核通过后新素材进入同一个人物，作品案例按 EXTERNAL Work 落地；支持独立模卡集合，不要求每张照片先建 Work。

**验收：** 原来源 A、本人来源 B 并存，B 上传可在审核后正常展示；旧 A 失效不会偷延长期限或放行旧媒体；上传完成但响应丢失不重复资产；照片＋PDF＋MP4 真文件通过；视频实际播放和 Range 通过；删除共享素材不误删无关原件。

### PR-04｜外部 Agent 摄取闭环

**交付：** 机器使用文档、schema／字典、摄取草稿、上传、去重提示、批量条目状态、提交审核及与已有 Person 的明确关联。

员工能够把摄取形成的人物发给本人认领。MCP 可后接，不能把“没有 MCP”作为不交付 API 闭环的理由；也不能用浏览器管理员 Cookie 来冒充 API 集成。

**验收：** 模拟外部 Agent 使用受限真实机器凭证完成“材料→草稿→后台核对→原 Person→邀请→本人接手”；来源和媒体都保留同一摄取追踪；机器无法访问其他 scope 或执行核验、分享、删除。

**至此可申请 Release A 阶段验收。** A 所有适用生命周期、升级、真实认证、真实存储、异步 worker、手机和正式镜像检查必须先完成；不能等 PR-08 才补，也不能只靠 MemoryStore。

### PR-05｜参考价与可用时间

**交付：** 本人参考价、内部议价、候选客户价三层读写权限；基础时间区间、更新时间与来源；内部目录可按明确口径筛选。

**验收：** 本人和客户无法通过详情、列表、错误、facet、历史、导出或浏览器响应得到内部议价；不同币种／单位不混排；“无档期记录”不被列为有空；更新自报价不改变已发客户报价。

### PR-06｜候选精选、客户分享与反馈

**交付：** 可同时精选 Work 和个人集合素材；展示许可；客户白名单快照；链接签发／撤销；客户手机页面、视频、偏好反馈和版本更新。

**验收：** 实际客户访问旅程不需要内部账号；不泄露内部字段或媒体标识；授权撤回、来源失效、素材隔离后后续访问关闭；GET 预抓取不改变状态；客户点击感兴趣不变成项目确认或预订。

**至此可申请 Release B 阶段验收。** 分享/反馈/衍生媒体的撤回、删除、升级、恢复和字节级隐私验收先完成，再开放客户链接。

### PR-07｜官网发布与撤回

**交付：** PUBLIC_WEBSITE 独立授权／人工批准；正式公开投影；经实际核对的 AnqiCMS 接口适配；发布与撤回 outbox、回执、失败提示。

**验收：** 未批准资料不会出现在官网；本人撤回后 OS 先停供，官网下架得到真实回执；失败保持待处理，不宣称下架成功。仅适配器 Mock 通过不算 C 完成。

### PR-08｜上线验收、迁移、容量和交接

**交付：** 汇总各阶段已经执行的基线升级、原数据核对、浏览器、PG 并发/恢复、性能、真实发送/COS 证据与交接手册；补全跨阶段最终回归，不把这些工作首次延后到本包。

数据库采用向前兼容、先加后切的策略。前端回滚不能让新外部凭证被旧接口接受；不能用回滚旧代码掩盖已写入新数据的迁移缺失。

### 19.1 停止继续扩张的条件

只要“本人扫码维护同一档案”或“内部按已确认维度找人”未闭合，就不得先开发 KOL 数据抓取、AI 排名、复杂排期、支付、平台分佣或全套经纪 CRM。

已有安全问题仍要修，但修复必须有明确受影响旅程和退出标准，不再无限增加与当前资源库无关的数据治理功能。

### 20.6 性能验收建议

## 23. 完成定义与禁止事项

### 23.1 可交付的定义

需求有页面入口、真实接口、数据库约束、权限边界、可恢复异常和运行证据；当前基线数据能够升级保留；新增实体可以撤回、删除、导出和恢复；用户能完成实际旅程而不理解内部技术模型。

以下任一情况存在，该工作包不得标“完成”：外部账号实际是内部成员；邀请只创建记录没有可用二维码／认领；视频只能看封面；本人上传强制沿用旧主来源；未绑定申请无法暂存；READY 草稿无回收；筛选字段有 UI 无数据；客户接口返回内部 DTO；确认来源等于认证资质；新增数据从导出／删除中遗漏；只有 Mock 而没有所需真实适配；生产 HTML 路由缺失。

### 23.2 禁止事项

不要重建另一套 Person／模特主库；不要修改已经应用的迁移；不要把原件公开化；不要取消来源过期／撤回检查；不要把全库 ADMIN actor 用在门户；不要在二维码服务、日志、存储或审计泄露秘密；不要用 AI 根据图片猜年龄、性别、国籍或资格；不要制造真实合作经历；不要将偏好当预订；不要把基础收人与选人需求扩大成完整交易平台。

不能为了“安全”继续让员工为每个普通字段操作多个技术对象；也不能为了“方便”删除后端边界。正确方向是让业务服务完成必要事务，让用户只做有业务意义的选择。

### 23.3 上线前环境条件

真实发信／短信配置、域名与 HTTPS、私有存储、媒体处理隔离、容量预算和代表性数据测试需要实际环境提供。开发 Agent 能完成代码与配置入口，但没有拿到并验证真实环境时必须准确列出缺项，不伪报，也不把环境缺项掩盖成代码完成。
