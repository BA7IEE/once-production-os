# ONCE Production OS｜BRD｜内部业务需求

版本：v0.3｜日期：2026-09-22｜当前范围：一期内部 OS + AI｜状态：文档已修订，产品实现和运行测试未执行

## 1. 决策与业务定义

用户已认可 ONCE Production OS，并明确这阶段先做内部系统，官网发布等可以暂不考虑。[U03，见13]

一期建设的是“制作资源与业务资料工作台”，不是官网内容中台、公开人才平台或制片ERP。其最小价值单元是：**下次接到需求时，不必重新找人、重新索要作品、重新确认已有信息。**

已有两三单海外成交是用户陈述，说明存在真实场景；不由此推断稳定利润、市场规模或平台收益。[U02] 一期不用Google收录、AI搜索引用、官网页面数和海外询盘增长作为验收指标。

## 2. 从第一性原理分解价值

一次制作合作需要知道：谁具备什么能力，有哪些真实作品，实际合作过什么项目，现在手里的资料是否可信、能由谁使用。文件、人物、作品和项目分开维护又相互关联，才有复用价值。

| 损耗 | 内部 OS 的对应动作 | 不承担的事情 |
|---|---|---|
| 聊天里反复翻人和图 | 统一人物、多职业、作品检索 | 不承诺自动发现全网人才 |
| 文件夹多、找不到对应作者 | 文件归源、作品署名、项目参与 | 不接管所有原始拍摄素材 |
| 同名/旧简介混淆 | 来源、核验时间、变更记录 | 不做人脸识别合并 |
| 找到人还要重新整理候选 | 保存内部清单、顺序和备注 | 不做客户门户、订档或自动成交 |
| 机械录入与中英整理耗时 | AI建议、证据对照、人工确认 | 不让AI确认身份、授权或商业事实 |
| 新同事无法接手 | 权限、清晰页面、JSON迁移、恢复手册 | 不靠个人聊天记忆运营 |

“内部可用”与“允许向客户、官网或第三方模型发送”不是同义词。本期只落实实际存在的内部用途和AI处理边界，不提前建设所有公开渠道规则。

## 3. 业务目标

B01：降低查找与重复整理时间。B02：统一事实与证据，避免人/文件/作品重复和归属错误。B03：限制内部敏感信息访问及未经允许的AI处理/导出。B04：提高内部候选讨论与项目交接质量。B05：可维护、可恢复、可导出，并支持后续模块连接。B06：用AI产生可测量的净时间节省。

旧B07“公开内容获客”保留为未来机会，不属于当前目标，不再在当前任务表要求达成。

## 4. 一期业务闭环与非目标

人员创建一条来源说明与人才草稿，可不填完整资料、不传文件、不写英文；随后补作品、署名与项目。已得到的资料有据保存、按角色和城市检索，保存内部候选清单。AI可协助提取和拟稿，人工接受之后才成为正式记录。

不做官网/CMS/SEO/GEO、对外分享或在线客户反馈。内部清单不假装“客户已看到”，内部项目日期不假装档期，内部复盘不假装已经获准公开的案例。

基础机构/品牌引用不是CRM；资料用途记录不是商业合同；AI调用预算不是财务；项目参与状态不是排期；中英内部说明不是网站发布。

## 5. 谁使用、谁负责

第一批用户是ONCE内部维护人、制片/资源协调人，以及需要查看资料的内部成员。模特、摄影师等作为被管理的职业主体，不因为被录入就自动成为登录用户。外部人员不能登录一期产品。

业务负责人确认试点边界、投入及资料处理依据；编辑整理事实；审核职责处理受限用途、删除和AI输入；维护者负责部署、恢复和秘密保管。小团队允许一人兼任多角色，不强制双人审批，但敏感操作必须显式确认、有记录。

## 6. 价值与投入判断

建议以“任务量 × 每次净节省时间 × 内部工时价值 − 持续维护成本”评价效率价值，不把未发生的收入或未来人才规模列为既有收益。净节省扣除补来源、核验、纠错、上传和维护时间。

一次性投入包括前后端、数据模型、选择性代码移植、测试、初始整理和运维交接。持续成本包括云资源、文件存储/流量、备份、AI调用和人的维护时间。预算、实施人和交付日期目前未确认；文档不报保证工期、报价或复用百分比。

不先采购新平台或更换官网部署。存精选图片/PDF/预览视频，原片继续使用原交付方式。可选择性复用SRVF工程机制，但要计入解耦成本。[R00～R15，见13；本轮继承证据，未再读代码]

## 7. 小样本试点

统一样本和默认值见12。先取最多30位可实际联系的人才、20组有来源作品、3个项目；不足按实际，不凑数量。重点覆盖模特、摄影师及至少一种其他角色。

| 衡量项 | 测法 | 一期建议目标/底线 |
|---|---|---|
| 找人和整理候选的净时间 | 同类历史重演与真实任务分开记录；目标各10次 | 中位数较手工下降30%，这是待验证目标 |
| 主数据可解释性 | 抽查名字/工种/作品归属/维护人/来源 | 无编造；缺项可见；重复可处理 |
| 内部协作 | 第二名内部人员接手一份候选与项目 | 无需原维护人逐条解释才能继续 |
| 核心可用性 | 断开AI后跑人工完整旅程 | 必须成功 |
| 基本安全 | 越权、失效用途、旧导出下载、未授权AI输入 | 对应产品用例通过后才用真实资料 |
| 可接管性 | 在隔离环境从备份恢复 | 结果可复核；未确认安全变化不能自动复活旧数据 |

这里没有“必须发布多少页面/获取多少询盘”的指标。AI不可用不应拖垮内部业务，但AI功能自身未实测时必须记录未验收，不能用人工路径替代其完成证明。

## 8. 继续与收缩条件

若资料能积累、检索有净节省、维护可接手，保持内部OS使用。若AI返工多，关闭对应任务而非否定整套系统。若某个专属表单很少使用，回到通用职业字段，不为未来准备复杂模型。

反之，若长期没有真实使用、录入负担高于收益，先简化表单和样本规模，不新增更多模块补偿。官网发布是否重启，由新的业务需求决定；它延期不会导致本期失败。

## 9. 底座如何承接以后

现在建立稳定人物/机构/品牌/项目ID、明确领域所有权、字段类型、版本和审计即可。未来CRM、报价、合同、排期、财务各有独立事实，通过已有ID引用；新领域不要回写人才表来充当自己的流程。

未来需要外部协作时再增加受限输出、授权、分享/发布状态与专用接口，不允许直接暴露内部DTO。此处只冻结连接原则，不预建空表、入口或供应商适配器。

## 10. 阶段与边界

唯一阶段定义见12：M0骨架；M1人工内部闭环及恢复基础；M2内部AI；M3整体试点和接管。条件名称使用 `ENABLE-*`，不与里程碑共用编号。

本期无官网启用门。采购、代码复制、真实数据、外部AI及内部生产入口各按实际动作确认，不能把“以后可能对外发布”变成当前开发前提。本文件不是法律意见，具体真实资料依据与保留时间由负责人按实际情况确认。
