# ONCE 后台 UI UX 整体解决方案

方案日期：2026-10-04
状态：已获用户授权并实施；本轮验收证据见 ../release/ADMIN_UX_IMPLEMENTATION.md
目标：让工作人员围绕收资料、维护档案、找人、组织候选和处理审核完成工作，减少对内部模型的理解、重复选择和跨页面寻找。

本方案基于已核实的 PR #36，提交 ccfe1406a77788fa01cb15290e4ccceb6b8fa382。参照现有 PRD、Talent Experience v1.1 及冻结合同；分析使用最新代码和历史页面证据，当前预览已停止，没有本轮运行中的用户测试结果。实现使用基于上述提交的独立工作树和 codex/admin-ux-solution 分支，保留后续业务链。

以下产品规则作为本轮实现目标。技术能力存在性与需要新增的部分单独列出；时间、通过率等验收指标是本方案建议值，不是现有实测成绩。

## 1 方案要解决的核心问题

当前问题包括：导航按管理模块展开、筛选表单压过人才结果、常用编辑藏在高级入口、人才选择没有自然承接、详情混杂邀请和授权表单、部分操作要求 UUID 或 JSON、保存及恢复规则不一致。

改造必须满足六条规则：

1. 每个常用动作有一个容易找到的主入口，其他入口进入同一界面和同一业务服务。
2. 用户看到某项资料时，就能在附近找到对应的维护动作，或知道为什么不能维护。
3. 每个选择都有明确后续动作；每次提交都有对象、状态和下一步。
4. 系统已经知道的对象和上下文不要求用户重复选择；不会替用户推断权限、来源、归属和核验结论。
5. 复杂规则在影响当前动作时解释，完整证据和技术编号留在有权限的详情中。
6. 正常路径、未保存、部分失败、未知结果、权限变化和资料冲突使用同一套交互规则。

### 范围

覆盖内部后台的主导航、工作台、人才目录、人才主详情、候选清单、照片视频及集合整理、作品项目、审核、邀请、导入、常用来源协作，以及对应的错误和结果反馈。

本人端保持独立认证与权限，只统一邀请衔接、提交和退回的业务语言；不在本轮顺带重建整个本人端。

保留现有 Person 身份、来源归因、权限、审计、命令回执、删除、导出和恢复规则。价格、档期、客户分享、官网发布仍按原阶段交付，本方案不增加占位菜单。生产迁移、合并、部署不属于本次方案工作。

## 2 信息架构与角色

### 主导航

| 入口 | 主要任务 | 页面不承担的内容 |
| --- | --- | --- |
| 工作台 | 看待办，继续近期工作，处理需要自己介入的异常 | 大量统计报表、无用指标和无行动入口的告警 |
| 人才库 | 找人、新增、维护同一份人才档案 | 单独的第二套人物库或专业人才库 |
| 候选清单 | 组织一次选角或内部协作所需的人与精选资料 | 客户访问、预订或报价 |
| 作品库 | 整理有明确案例身份与署名的作品 | 把每张照片强制建成一个作品 |
| 项目 | 记录真实项目、参与人员和关联作品 | 交易、合同、账款或排期系统 |
| 审核 | 处理本人提交、归属申请、外部材料和核验协作 | 把不同审核含义合成一个“全部认证” |
| 管理与设置 | 低频治理、系统配置、资料工具和操作记录 | 取代对象页的日常维护入口 |

管理与设置在侧栏底部，默认收起；进入后按“资料工具”“协作与权限”“系统维护”分组。资料来源、全局素材、导入导出、AI 配置、机器接入、合并、删除任务、成员、字典和审计保留在这里。

日常使用仍能从人才页上传照片，从作品页加素材，从当前对象发起核验；需要跨对象集中处理的人可以使用管理入口。入口移动不影响服务端权限检查。

### 角色和入口状态

不新建第二套角色体系。沿用权限，按当前职责呈现工作内容：

- 资料维护者：新增、补资料、传图、送审及自己发起的任务。
- 选角人员：搜索、对比、候选清单和当前可见资料。
- 审核者：待自己处理的申请、差异和依据。
- 管理员：上述业务能力，加上管理与设置；登录后仍先进入工作台。

入口是否可用同时考虑权限、当前对象状态和部署能力。敏感且无权知晓的入口隐藏；用户有权了解但暂时不能执行的动作显示原因和可行下一步。没有实现或未开放的阶段功能不出现在业务导航里。

## 3 工作台

首屏按“待我处理”“最近打开”“快捷开始”组织。

待办使用业务对象作为标题，例如“林禾提交了 3 项资料修改”“王晨的资料等待确认团队可见范围”。每项展示谁发起、当前在等谁、最后变化时间，以及一个明确动作。

“待我处理”与“我发起的、正在等别人”分开。没有待办时显示正常空状态，不生成虚构任务。来源即将到期等提示应能直接进入对应处理流程；没有可靠汇总能力时，不显示伪造的总数。

快捷动作采用“新增人才”“找人加入清单”“导入资料”。有权限且确有未处理审核时，再出现审核入口。

最近打开的数据遵守账号与范围隔离。首版可使用当前会话的受控状态；若要跨设备持久化，需单独实现服务器存储，不假设已有该能力。

## 4 人才目录和候选选择

### 页面布局

~~~text
人才库                                      新增人才
搜索姓名或艺名                 职业       城市       筛选

已生效：模特 ×  深圳 ×  身高170–180 ×       清除条件
共 86 位                                      照片 / 列表

人才卡片     人才卡片     人才卡片     人才卡片

已选 3 人                             取消选择  加入候选清单
~~~

此为结构示意，数字为示意数据，不是现有系统统计。

默认展示人才；普通联系人通过明确的次级切换进入，不能默默消失，也不能自动转成人才。

通用首屏保留搜索、职业、城市。“筛选”打开独立侧面板；模特场景提供性别、国模或外模、从业类型、年龄、身高、拍摄类型的常用分组。其他职业不显示不相关的模特条件。

多选使用带复选框的选项列表和可移除标签。年龄预设和自定义范围择一展示；身高上下限组成一个“身高范围”控件。保留现有同维度 OR、跨维度 AND、未知值、当前量尺和同作品匹配语义。

### 筛选生效规则

选择条件后点击“应用筛选”；搜索框按 Enter 也可执行。面板内修改尚未应用时明确提示，结果数继续对应上一次已生效查询，不能拿新条件配旧数量。

已生效条件在结果上方显示，逐项移除可直接重新查询。重置范围明确；不能顺便清空候选选择。

查询期间保留已有结果轮廓并显示加载状态，结果未与当前查询对应时禁止基于旧结果继续执行批量操作。筛选返回后再更新数量；失败保留原条件并提供重试读取。

有结果时，在 1280×800 的桌面视口不滚动即可看到第一排人物照片、姓名和关键资料。手机首屏应能开始搜索并看到实际结果，不能被默认展开的筛选项填满。该项属于拟验收的布局要求，尚未实测。

空结果显示当前条件和减少条件的入口。不自动放宽筛选，不把未知年龄、未知身高算成符合。

### 卡片和选择

卡片主体打开详情，独立复选框只负责选择，二者不互相触发。卡片显示封面、姓名、职业、城市及该职业重要资料；版本号和技术编号不进入主视觉。

同一人才有多个职业时，先允许选中该人，加入前明确“本次作为哪个职业”。只有一个无歧义的适用职业时可以预填，并在确认摘要中展示。前端必须区分“待选职业”与普通联系人的无职业状态，不能把二者都编码为 null 后发送。

当前安全状态结构已限制最多 200 个 Person＋Role 选择；实现应保留明确上限和跨页计数，不能静默截断。多职业选择计数同时解释人数和候选条目数。

翻页、看详情再返回保留已生效条件、页码、滚动位置和选择。按当前身份与权限重新读取，不能为恢复位置而继续显示过期敏感资料。刷新恢复只承诺安全规则允许的状态；不将姓名查询、档案正文或媒体详情新增写入 URL、localStorage 或 sessionStorage。

不提供含糊的“全选所有搜索结果”；首版只提供“选中本页”，跨页累计选择始终可查看和取消。

### 加入候选清单

勾选后出现底部操作栏，包含人数、取消选择、加入候选清单。该栏不遮挡末行内容，键盘和手机均可操作。

选择清单使用可搜索、可分页的选择器，不默认提交到列表第一项。允许在选择器中明确新建内部清单，再继续原有选择；新建仍使用现有标题和范围规则。

提交前显示目标清单、人物、职业、已经存在的条目和当前不可用项。重复项明确标记，不悄悄新增或改备注。

批量加入采用一个应用层命令、一次明确提交和一个可核对的批次结果，服务端逐项复查权限、Person、Role、清单版本和相关依据：

- 新增可提交项在同一事务完成；已存在且当前可见的精确重复项返回“已在清单”。
- 任一待新增项失效或权限变化，本次新增整体不写入；列出当前允许展示的原因，用户明确调整选择后再提交。
- 权限失效的对象不能通过失败信息继续泄露姓名或详细资料。
- 网络结果未知时先只读核对本批结果，不创建新键再次加入。
- 成功提示具体数量与目标清单，提供“查看清单”和“继续找人”；清除已成功处理的选择。

现有接口只确认具备单条 shortlist.itemAdd，批量应用命令属于新增能力，不能用并发调用单条接口模拟原子成功。批量上限需在现有 200 项选择上限内完成真实数据库测量；若既定事务预算无法承载，必须在合同评审中明确收窄单次提交上限，不静默拆批。

## 5 一个稳定的人才主详情

主详情使用独立地址，保留“返回结果”上下文。页头展示姓名、职业、当前可见范围，以及加入候选、编辑资料和更多操作。

固定分区为“概览”“基本资料”“照片视频”“作品与合作”。联系与经纪在有权读取的资料区出现。邀请本人维护、团队可见范围、来源依据、变更历史、归档等由页头更多操作进入相应抽屉或完整任务页。

旧人物详情和专业工作台不再作为日常主路径。其已有业务能力逐项迁入对应分区；完成能力对照和权限回归之前，不删除服务或遗留处理入口。旧可访问链接逐步转向同一主详情。

### 概览

优先展示照片、重要基本资料、代表作品和确有必要的待处理事项。没有本人维护需求时不展开邀请表单，没有已认领账号时不铺设空的开放字段列表。

缺失资料显示“未填写”；未确认、失效、受限和待审核分别表达，不能统一用“未知”或一个绿色“已认证”覆盖。

资料完整度只可用于帮助补资料，不作为人才评分，不因缺少敏感字段降低分数。本轮先显示具体缺项，不建设复杂评分系统。

### 编辑

页头“编辑资料”定位到基本资料区域；每个区域直接提供明确操作：

| 区域 | 常用内容 | 保存含义 |
| --- | --- | --- |
| 姓名与简介 | 姓名、艺名、别名、介绍 | 保存这些身份文字 |
| 个人资料 | 已明确提供的性别、国籍、出生信息、常驻地 | 保存当前允许修改的对应事实 |
| 职业与能力 | 职业、语言、能力、职业专属分类与意愿 | 维护本人的对应职业事实 |
| 量尺 | 身高、三围、尺码、测量时间及精度 | 新建或维护可编辑的量尺记录，明确是否另行确认 |
| 联系与经纪 | 当前有权读取和维护的联系、代表关系 | 保存受限资料，不扩大接收人 |

每个编辑区具有明确保存边界和固定的“取消／保存本区资料”。同一时刻只激活一个编辑区，切换前处理未保存内容。用户不需要在“人物”和“专业人才”之间切换。

一张小表单若跨多个已有命令，必须缩回清楚的保存单元，或增加经过评审的原子应用命令。禁止前端调用一串写接口后统一声称“全部保存成功”。

来源处理使用用户能理解的两种意图：“修正原资料的录入”“收到新资料，补充更新”。前者沿用并复查原依据；后者引导补充独立来源或进入已有修改建议流程。跨来源依赖仍由服务端逐项验证，不为减少步骤错误归因。

历史量尺和已经确认的记录不原地覆盖。日期没有提供就留空，不把当前日期伪装成测量日期。保存信息、采用本人声明、确认字段与来源一致、核验证书或成年资格始终分开。

## 6 照片视频和作品整理

### 人才页直接上传

从“照片视频”点击“添加文件”，选择或拖入多个文件。在确认区展示本批来源、目标人才、可见范围和每个文件。

已知上下文可预填；已有来源仅在确属本次资料且仍有效时使用，新收到的资料提供就地补充来源的入口。不能将新文件默默归到历史来源，也不能自动转成已核验或团队可见。

上传队列逐文件显示：待上传、上传中、处理中、可使用、失败、待核对。上传完成与资料检查完成分开，只有正式可用后才进入相应照片展示或封面选择。

一次多选、逐文件处理，取消、继续编辑和离开提醒都有明确结果。默认逐文件串行写入以复用现有未知结果保护和配额控制；并发优化在单独验证每文件命令隔离后再考虑。

| 情况 | 页面表现 |
| --- | --- |
| 其中一个失败 | 已完成文件保留，失败项显示具体处理方式；不重传全部文件 |
| 已知未提交的本地文件 | 可以移出队列，不产生服务器删除 |
| 文件已经接收但处理未结束 | 明确显示仍在处理，读取状态，不假报成功 |
| 返回结果未知 | 冻结该项的写入，核对原上传，不用新请求自动再传 |
| 用户取消已开始上传 | 使用现有取消和清理规则，显示取消状态；不能假装文件从未到过服务器 |
| 已经成为正式素材 | 通过独立删除流程处理，不拿“取消上传”绕开删除保护 |
| 关闭页面 | 未传文件需重新选择；已接收文件可按当前账号读取服务器状态 |

主详情中的照片区与上传组件共用一份展示结果，消除同一素材重复显示两遍的结构。单个上传区的成功状态驱动重新读取，不要求用户去另一个模块“刷新素材”。

保留现有文件限制和类型支持；PDF 仍为附件，不增加 OCR；视频实际播放能力按既有受控接口。用户页面说明文件要求和处理结果，不陈列校验值、存储键、Worker 等内部实现词。

封面在当前可用图片中选择，给出清晰的预览与保存结果。图库只是组织方式，不因此获得额外发布或导出许可。

### 集合与作品

用户使用“模卡”“素颜照”“作品照片”“介绍视频”“作品案例”等业务名称。添加到某组时，选择文件、上传、归类和关联在同一任务中完成；无需先研究 MediaCollection 与 Work。

有具体案例身份、描述和署名的材料使用作品案例。只有一组照片时允许放入作品照片，品牌和年份未知可以留空。外部作品与 ONCE 实际项目合作保持清楚区分。

集合、作品与素材引用复用现有身份；共享素材不复制成新原件。移出集合、取消候选精选、删除原件是三个不同动作，文案与服务端行为一致。

作品页中直接选择素材和贡献者。关联人物使用可搜索选择器，显示用户有权看见的区分信息；不能要求普通操作者粘贴 UUID。

## 7 审核与邀请

### 一个审核入口，不同业务决定

审核页按“待我处理”“我发起的”“已处理”组织，并可按资料更新、归属申请、外部材料、团队核验筛选。

同一个人一次提交作为一条任务。列表回答：谁、改了什么、何时提交、当前在等谁。进入任务后保留该人的上下文和返回位置。

资料变更采用旧值与新值对照、媒体缩略图和简明来源说明。依赖组用业务语言表示，例如“这个案例及其署名”，组内选择联动。冲突项单独说明，不能在后台版本已变化时直接覆盖。

主要动作是“采纳所选修改”“退回修改”；退回显示给本人看的说明与内部记录分开。涉及独立归属、监护关系、成年或证书核验时使用对应流程，采纳资料不自动获得这些结论。

批量审核仅在已实现、权限允许且同一依赖规则成立的范围开放；不提供一键通过所有不同类型任务的快捷按钮。

同一审核入口是展示层整合。原有 Submission、Claim、SourceReview 等身份、权限、审计和写入合同保持独立。统一分页和统计需要后端只读聚合时，增加受权限约束的查询投影，不新建工作流引擎。

### 团队核验与共享

在人才详情上直接发起“提交团队核验”，自动携带当前人才。用户只选择真正需要决定的核验人、目标范围、确认共享的人和有效期限。

界面按以下进度解释：草稿仅本人可见 → 等待核验 → 等待确认共享 → 指定团队可见。实际核验、接受、发布权限不合并；状态变化不会自动确认所有字段或开放受限联系方式。

需要用户授权某人读取材料时，在该动作内明确展示材料和对象。技术上不同的权限决定可以在一条引导任务中完成，但不能替用户自动批准。

### 邀请本人维护

邀请从人才详情进入。界面展示目标姓名、接收方式、当前准备开放的具体内容和有效期，完成后给出明确可复制的链接或二维码。

“创建邀请并生成链接”可将已有多次调用组织成一次可理解的任务，但要保留中间结果：邀请已建但签发失败时继续同一邀请，不重复创建；签发结果未知时先核对，再由用户明确撤销或重签。

生成链接不自动向外发送消息；本方案不增加发送供应商。凭证不进入日志或浏览器持久存储，关闭后无法再次查看的一次性内容要在当时说明。

领取邀请、确认归属、批准本人可见字段和取得本人用途同意是不同步骤。邀请成功不代表本人已经能看整份内部档案。

## 8 候选清单和项目协作

候选清单首页先展示清单及其用途；进入某份清单后主要展示已选人物，提供“继续找人”。

从人才库加入与从清单继续找人，复用同一目录组件、同一查询合同和同一批量加入命令。区别只是是否已有明确目标清单。

清单项显示人物、此次职业、备注、选用资料和当前可用状态。已有条目不因资料失效悄悄消失：按当前权限保留可展示的最小状态，告诉用户需要重新选择；不得显示已无权读取的原内容。

更改顺序、编辑备注和移出清单分别有明确保存结果。移出清单不删除人才；撤销若有提供，必须是经过当前权限和版本检查的补偿命令，不是简单恢复旧前端数组。

项目参与、候选意向、确认参与、实际合作分别使用现有业务状态。加入内部候选不会写出“已预订”或“档期已锁定”。客户分享留在后续阶段。

## 9 导入和低频治理

普通导入提供 CSV 或粘贴表格入口，步骤为“选资料 → 对应字段 → 看预览 → 确认导入 → 查看结果”。字段选择显示中文，内部稳定代码由字典映射。

同名、城市别名、未知职业和缺失列逐项提示；不能自动合并、猜映射或吞掉数据。进入提交前明确本批来源、类型和可见范围。部分完成按行展示，提供失败行修正和已有记录链接。

现有新导入使用 V2 业务合同；表格解析、字段对应和错误定位属于待实现的前端能力，不能把现有 JSON 文本框改名成“Excel 导入”。首轮不承诺原生 XLSX；JSON 保留为管理工具中的高级格式。

治理操作从当前对象的更多操作进入，再由管理页集中查任务。普通归档按已有可逆语义处理；合并、不可逆删除和扩展访问范围保留明确的影响预览与确认。

风险决定要准确解释涉及什么、影响谁、能否恢复。重复出现但不要求任何决定的安全长段落移到可展开说明；必要的授权和不可逆后果始终保留在提交前。

AI 辅助整理优先在当前资料上下文中提供，只有数据用途、配置、预算与权限满足时才可发起；输入预览和人工采纳保留。集中任务与配置仍可从管理入口访问，不增加自动外送或自动采纳。

## 10 全站统一的交互规则

### 页面和弹层

- 列表、人才详情、完整审核、复杂作品编辑使用独立页面和稳定路由。
- 抽屉处理短任务，如选择清单、查看来源、发起邀请。
- 对话框处理小量输入或重要确认；不连续套三层表单弹窗。
- 返回优先回到原任务和原位置；从外部直接打开详情时，返回对应列表。
- 旧链接的迁移不绕开认证；SPA 回退不覆盖 API 路由。

### 保存与离开

编辑时显示具体未保存区域和固定操作栏。按钮命名说明保存范围；成功后在原位置显示已保存，并重新读取权威结果。

页内切换、路由跳转和关闭抽屉统一检查未保存改动。浏览器刷新或关闭标签使用其支持的离开提醒，不承诺浏览器一定允许拦截。

内部表单首版使用显式保存，不新建通用自动保存平台。已保存的人才草稿在服务器；尚未提交的编辑正文在当前页面内存。本人端已有服务器草稿继续使用其合同。页面不会以“自动保存”名义把敏感正文放入浏览器存储。

### 请求状态

| 状态 | 展示和允许操作 |
| --- | --- |
| 尚未保存 | 显示改动范围；保存或放弃 |
| 正在提交 | 锁定本次提交相关控件，阻止重复提交，允许浏览不冲突的其他资料 |
| 已确认成功 | 明确对象和结果；读取失败只重读，不再写一次 |
| 明确拒绝 | 仅在已确定未执行时允许修正后重新提交；保留输入并定位原因。未知结果后收到 4xx 不得据此释放原请求 |
| 结果未知 | 明确告诉用户当前无法确认，保留原请求身份，沿用现有未决提交限制；可继续获准的只读浏览，不为界面便利放开受阻的新写入 |
| 资料版本变化 | 展示当前可见的新旧差异，用户重新决定，不自动覆盖 |
| 登录失效 | 暂停身份，同一身份恢复后核对；其他账号不能看到或重放原请求 |
| 当前权限已收回 | 清除已不允许展示的内容；保留最小状态和安全返回入口 |

“核对结果”按钮只读取状态。需要原样重放时，使用语义明确的独立动作，保持原账号、原键和原内容，不把可能发出写入的行为伪装为只读检查。

内部刷新后只剩允许的未决标记时，需要受当前账号和领域权限限制的回执查询入口。没有原编号、不能精确对应或找不到回执，都不等于未执行；仍保持待核对。该能力缺口见第 12 节，不能通过放宽浏览器存储规则解决。

### 文案与视觉

按钮使用“动作＋对象”，例如“加入清单”“保存简介”“提交核验”“查看处理结果”。取消和关闭含义一致。正常路径不显示 Person ID、dependencyGroup、revision、schema 或回执 UUID；有权排障者可展开复制必要编号。

界面用中文为主，减少大段英文装饰标题。建议采用 4/8 像素间距体系，正文 14–16 像素；标题、辅助说明、状态和操作有稳定层级。颜色主要表达操作与状态，不以颜色作为唯一提示。

采用一套成熟组件库和项目内统一封装，建议优先评估 Ant Design 与既有 React、CSP 的兼容。组件库选型验证在实施首片完成，不用更换组件代替流程改造。

所有核心操作支持键盘，焦点清晰，标签与输入关联；弹层关闭后返回触发点，错误可定位到字段。手机关键触控区建议不小于 44 CSS 像素。对比度、读屏、缩放和弹层焦点需要真实检查。

内部桌面重点验 1280、1440、1920 宽度；内部手机重点验找人、详情、候选和短审核。已有本人端 360、390、430 宽度的完整维护能力作为回归边界保留。不能仅凭“页面没有横向溢出”宣称手机好用。

### 读取性能

列表按现有分页合同读取轻量摘要和缩略图，不为每张卡片加载整份专业档案；详情按可见分区加载，来源历史和管理数据按需读取。页头和首批结果先呈现，不能为不相关的后台数据等待整页完成。

实施前后使用同样权限、同样样本、同样网络条件记录首屏、筛选和详情读取耗时及请求数量，遵守既有参数文档和服务预算。没有测量前不宣称提速；出现逐卡片重复查询或原图下载，应先修读取方式，再考虑缓存。缓存不能绕过当前权限、来源失效或撤回检查。

## 11 成熟做法及本项目的取舍

- Ant Design 的直接操作强调内容与输入保持上下文；本方案用于详情就地编辑、任务内选择和减少弹层跳转。[Make it Direct](https://ant.design/docs/spec/direct/)
- Ant Design 的保持页面上下文指导按需展开和减少打断；本方案不把长流程全部塞进一个弹窗。[Stay on the Page](https://ant.design/docs/spec/stay/)
- IBM Carbon 的表单规范强调渐进展示、必填规则一致、字段级错误及可修正方向；本方案用于筛选、资料录入和审核反馈。[Forms](https://www.carbondesignsystem.com/building-blocks/core/patterns/forms)
- Shopify 的 Save Bar 明确未保存、保存、放弃和离开保护；本方案借用统一保存行为，不照搬电商对象和功能。[Save Bar](https://shopify.dev/docs/api/app-home/latest/apis/user-interface-and-interactions/save-bar-api)

这些是官方公开设计规范的参考，不是本项目已经采用的组件或已经取得的体验效果。

### 实施边界

前端优先按业务功能组织：页面外壳与导航、人才目录与详情、候选清单、审核、媒体、通用反馈。避免继续将新功能塞进 main.tsx 的大条件分支，也不建立通用低代码平台。

业务写入仍经过现有应用服务、权限、writeAhead、审计和回执。新增批量命令复用领域校验，不能由前端循环伪装事务。新增只读投影在计数、分页、排序之前执行当前可见性约束，读取失败不能显示成零待办。

拟调整的主要文件区域：

- apps/admin-web/src/main.tsx、ui.tsx、style.css 及拆出的导航和页面外壳。
- talent-directory、talent-directory-detail、talent-ui、talent-edit、talent-intake、directory-state。
- shortlist-ui、media-ui、internal-collections、work-case-ui、production-ui。
- talent-review-ui、source-review-ui、talent-handoff-ui、pending-ui、api。
- 必要的契约源、核心应用服务、API 路由和针对性验收；generated/requests.ts 必须由正式生成流程产生。
- docs/design、对应 release 文档及版本绑定证据。

旧后台产品化分支只作为可复用实现参考。当前功能链已经包含后续身份、来源和媒体规则，不能直接整支覆盖或合并旧界面后宣称升级完成。

已有迁移 1–75 冻结。界面改造本身不需要迁移；若新增服务必须增加持久化字段，先明确模型、导出重建、删除、合并和恢复影响，再追加 76 及后续。不得预先建设通用任务表、全新人才库或第二套权限模型。

预览必须标明当前提交，使用与该提交匹配的服务和数据库。以完整新旅程作为内部评审入口；旧功能在迁移期间保留受控兼容，不向用户暴露多套同名入口。

如有功能开关，回退只切换已证明兼容的页面实现，不回退 schema，不抹除新数据，不恢复失效权限。PR、合并、部署和真实供应商验收继续单独记录。

## 14 验收方案

### 真实业务验收

| 编号 | 任务 | 必须看到的结果 |
| --- | --- | --- |
| UX-AT-01 | 只输入姓名和职业建档 | 同一 Person 草稿；直接到主详情；说明当前可见范围 |
| UX-AT-02 | 修改姓名和简介 | 无需高级管理；保存范围明确；再次读取一致 |
| UX-AT-03 | 更新资料及量尺 | 原来源与新资料正确区分；未知日期保留；确认与保存分开 |
| UX-AT-04 | 上传三份文件并设封面 | 逐文件状态可解释；成功项保留；允许的图片设封面后列表与详情一致 |
| UX-AT-05 | 跨页选三人加入已有清单 | 选择不丢；职业明确；目标明确；重复与无权限项有真实结果 |
| UX-AT-06 | 选择后新建清单继续加入 | 不丢原选择；新清单与加入分别有可恢复结果 |
| UX-AT-07 | 查看详情后返回结果 | 查询、页码、位置、选择正确恢复，不泄露失效资料 |
| UX-AT-08 | 审核本人一次更新 | 对照差异；依赖联动；采纳不冒充资质核验；退回说明可继续修改 |
| UX-AT-09 | 从人才页发起团队核验 | 无需再找人；责任人和范围清楚；核验后仍需有权者明确共享 |
| UX-AT-10 | 生成邀请及处理归属 | 邀请身份不混淆；成功可用链接；未知签发不重复生成 |
| UX-AT-11 | 导入一批含错误的表格资料 | 中文字段映射；逐行预览与结果；同名不自动合并 |
| UX-AT-12 | 在作品中加素材和署名 | 任务内选择；源素材不复制；外部作品不制造 ONCE 实际合作 |

必须追加真实反例：提交成功但响应丢失；保存成功后读取失败；会话过期与换账号；权限或来源中途失效；并发改同一条记录；文件部分失败；离开未保存表单；批次中一个人才失效；角色重复或变更；手机窄屏和键盘路径。

核对既有 Person ID、来源、审计、回执、历史、导出重建、删除、合并和恢复没有因界面迁移漏项。受影响检查与当前 head 绑定；供应商模拟与真实环境分别记录。

### 用户可用性验收

让不参与开发的代表性业务人员只拿到任务目标，不提供按钮名称、菜单位置或点击顺序。至少覆盖资料维护、选角和审核三类职责。

首轮建议 5 人用于发现问题，不据此推算总体满意度。修复后建议至少 10 人执行六项核心任务：建档、编辑、上传设封面、找人加清单、审核、处理一次保存异常。

建议收口门槛：

- 每项核心任务至少 90% 的参与者无需口头指路完成。
- 不能出现误扩权、重复建档、误删原件、把未知结果当失败重写等关键错误。
- 普通任务中不要求用户输入 UUID、JSON、字典代码或原始错误码。
- 每个人都能说明刚才修改了什么、有没有保存、谁能看到和下一步在哪里。
- 记录完成时间、走错入口次数、提示次数和用户解释；与现有后台同样任务比较，不能只测新界面。

以上比例是产品验收建议；样本规模有限，不代表统计意义上的总体效果。观察到的严重问题优先处理，不用平均值掩盖。

### 验证与运行边界

本轮仅编制方案，代码测试、浏览器、数据库、构建、供应商验证全部未运行。

未来验证遵守 RESOURCE_LIFECYCLE：重型任务串行，沿用资源门槛和受控资源归属。真实 PG 与浏览器不得为了产出绿色结论绕过门禁；可以使用合规独立 CI，保留失败和最终 head 的证据。

“功能正确”“界面完成”“无提示用户验收”“真实供应商验证”“生产部署”分别报告。任何一项未做均标记 NOT_RUN，不用“完美”“全绿”替代具体结论。

## 15 评审时需要确认的产品选择

本方案已经给出默认选择，不依赖逐项追问才能继续评审：

- 日常主导航采用六个业务入口，管理与设置置底。
- 人才只有一个主详情，常用资料可就地编辑。
- 筛选采用明确应用，已生效条件可见；选择与搜索条件互不混淆。
- 批量加入首版采用原子新增，失败不悄悄部分写入。
- 内部编辑显式保存，不承诺尚未实现的自动保存和跨设备草稿。
- 上传队列先保证逐文件正确和恢复，首版串行处理。
- 审核统一入口，保留每类决定的身份、权限和含义。
- 管理规则继续严格执行，由界面准确解释其业务后果。
- 原生 XLSX、保存视图、跨设备工作进度和后续 B/C 功能不扩入本轮。

评审重点是这套任务路径是否符合实际工作，以及实施和验收边界是否明确。方案确认后，第一份可交付结果应当是可审阅的核心流程原型与契约清单，随后进入真实功能切片。
