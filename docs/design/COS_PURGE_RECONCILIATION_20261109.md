# COS 清理核对：隔离实现与未决条件

状态：保守补丁待审、未部署；真实 COS **NOT_RUN**。基线为
`20220e9554f1314a866f8e53e9ecb12629defbe7`，本文件描述其上的变更，
不把基线已通过的 CI 当作本补丁的验证。

## 问题和已实施的保护

腾讯云 [GET Bucket（List Objects）](https://cloud.tencent.com/document/product/436/7734)
明确说明新上传对象可能暂时不出现在列表中。`Contents=[]`、一次 HEAD 404、
一次删除响应或若干次延时重试都不能证明某上传命名空间没有未知对象。
尤其是客户端 PUT 超时后，服务端仍可能在之后完成该写入。

当前实现以 `uploadId` 为边界：

1. 为新版接收、COS 写入和命名空间清理使用同一持久锁 inode，
   不删除锁文件；新版进程之间不得同时执行冲突操作。锁文件只协调共享同一
   媒体根目录的新版进程，不能约束旧程序、其他媒体根目录或外部写入者；
   文件系统必须正确实现跨进程 flock 和目录 fsync，这里没有验证多节点、
   网络文件系统或断电持久性。每个上传保留一个锁文件，需要容量治理。
2. 发 PUT 前创建不可覆盖的 `.cos-publishing`，同步文件和目录；成功写入后
   才删除标记并同步目录。错误、超时和进程崩溃保留标记，同一 token 的重试
   不得覆盖标记。清理遇到标记时保留隔离目录、拒绝确认。隔离后的 uploadId
   不允许被新版 `receive` 再次建立。
3. 将本地 group 移到 `trash/<uploadId>` 后，同步父目录；对来源于已校验的
   `work-<token>` 目录、清理意图 token 和 COS 列表的候选做并集，严格限制
   uploadId、token、零件名与数量。先校验整个本地目录及列表响应的格式和
   未截断标志，再对
   每个已知的精确键发送删除请求；不依赖列表才能发现已知键。未知条目、
   链接、冲突目录、截断列表或过多 token 阻断操作。
4. COS worker 先检查全部已知对象，拒绝不经过命名空间回执的逐对象删除。
   `trash/<uploadId>/.cos-reconciliation.json` 记录目标身份摘要、候选键、
   候选来源、列表观察及逐键结果。回执为私有文件，原子替换并同步文件和
   目录；发 DELETE 前先持久化 `UNKNOWN`，返回 200/204 后记
   `ACKNOWLEDGED`。超时、异常、404、异常状态码和进程死亡均不算确认。
   原始 SDK 错误和凭据不进入回执。**ACKNOWLEDGED 只表示已收到该请求的
   成功响应，不表示命名空间已清空，更不证明供应商底层介质擦除。**
5. 回执始终是 `RECONCILIATION_REQUIRED`，已有回执的后续自动清理直接停止，
   不再重复读取桶或删除对象。所有 COS 路径仍抛出待核对错误，保留隔离目录；
   不调用成功收口；worker 对每个 COS 对象也保持 `UNKNOWN`，不把单次 HEAD
   404 持久化成 `MISSING`，因此不得标记物理删除成功或据此释放额度。失败可能已经
   删除了部分已知对象。

本地目录只是候选来源，回执不是完整、不可篡改的历史账本；一份现存回执不
能用作恢复旧状态后的授权。自动化重试停止是刻意的可用性限制。中断发生在
回执原子替换前可能遗留临时文件；发现不认识的文件时清理会停止并保留现场。
不要手动删回执、标记或隔离目录来迫使任务继续。

## 允许最终完成之前仍需实现和验证

当前补丁**没有实现 COS 清理的自动最终完成**。最少需要：

- 在首次允许云写入之前，为每个上传建立有完整起点和目标身份绑定的持久
  对象清单；在每个 PUT 之前写入并同步包含精确键、尝试身份和状态的记录。
  遗留上传、丢失记录、旧版本写入及外部写入必须归为未知，不能从空目录
  或空列表推断没有历史对象。
- 使用可核查的写入栅栏及供应商明确支持的请求结果/静默屏障，证明没有
  在途或迟到的写入还能提交。进程锁释放、重启、超时、重试或 HEAD 404
  自身均不足以证明这一点。对已知键执行删除后，应以经过确认的供应商
  合同定义每个终态；[DELETE Object](https://cloud.tencent.com/document/product/436/7743)
  对启用或暂停版本控制的桶可能创建删除标记，不能将标记当作各版本清除。
- 将清单、未决写入、清理回执和不可复用的栅栏与数据库备份一致地保存、
  恢复和核对；检测缺失、回滚、分叉、目标更换和版本混用并保持 UNKNOWN。
  当前 `backupPrivateMedia` 只打包当前媒体与数据库状态，不包含完整 COS
  写入历史或这些回执，不能提供上述证明。
- 以受控请求证据核对每个已知键和完整清单、保护审核与幂等收口；对于历史
  漏记或无法证明已静默的写入保持未决。不得用人工勾选、任意回执文件、
  空列表或短暂等待替代这些证明。
- 获得明确授权的独立非生产桶、隔离前缀、最小测试身份及零费用确认后，
  单独执行真实供应商验证；模型替身、SDK 回环和真实 PostgreSQL 不能替代。

现有代码不支持从未决回执进行受审计的恢复或最终完成，也未提供实现以上
完整账本、恢复兼容或供应商静默屏障的生产方案。部署前必须完成设计复核与
这些工程工作；迁移 1—85 保持原样。
