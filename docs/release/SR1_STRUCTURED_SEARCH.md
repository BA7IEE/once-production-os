# SR1｜结构化人才检索与命中依据

版本：0.1.0-dev.1｜输入：SL1 `b2654b2`｜范围：FR-14 第一批内部检索

## 1. 目标

把原有“人才列表筛选”升级为可用于内部找人的结构化检索，同时让每条结果解释为什么命中。当前不做模糊匹配评分、推荐排名、档期/预算/国籍推断，也不把未知字段当成满足条件。

本批没有新增数据库表或迁移；检索读取现有 Person、FieldEvidence、Work/WorkCredit、Project/ProjectParticipant 事实，并在当前请求里重新执行来源、范围和权限判断。

## 2. 当前支持的条件

- 姓名/别名关键词 `q`；
- 角色、城市、工作语言、技能；
- 人才档案状态；
- 参与作品关键词与作品制作归属；
- 是否存在当前可见、已记录为 `ACTUAL` 的项目参与；
- 对角色/城市/语言/技能要求最近 N 天内有当前值的人工核验。

`verifiedWithinDays` 只能与上述四类直接资料条件一起使用。核验记录必须对应当前字段值、当前来源 revision，且来源此刻仍可读；字段或来源变化后，旧核验不能继续证明当前值。

## 3. 命中解释

结果返回 `match`，包括：

- 每个直接条件的字段、值、核验状态和核验时间；
- 当前可见的实际项目数量与少量示例；
- 当前条件命中的作品及人才在该作品中的角色；
- 当前档案明确缺失的城市/语言/技能字段。

服务端同时返回语义声明：排序为最近更新优先、`scoring=false`、实际项目只表示 `VISIBLE_RECORDED_ACTUAL_ONLY`，以及当前明确不支持 `availability / budget / nationality`。

这些字段用于解释数据库里当前有权读取的事实，不是能力评分，也不证明系统之外不存在其他经历。

## 4. 权限与反例

- 人才、作品、项目各自按当前来源和原生 scope 重新鉴权；关联不会扩权。
- H1 基本资料交接只能让接收方搜索到获准的基础档案，不能借检索得知其私有作品或项目关系。
- `NOMINATED`、`CONFIRMED` 不计实际项目；只有 `ACTUAL` 计入。
- 作品关键词只在当前可见 Work 中匹配，并要求存在 WorkCredit；上传过文件不等于作品经历。
- 城市/语言/技能为空时只标记未知，不满足对应筛选。
- 不从姓名、照片、语言或城市猜国籍；当前模型也没有档期与预算事实，因此这三类筛选显式不支持。
- 当前没有未校准百分比、综合推荐分或“最佳人选”排序。

## 5. 接口和界面

新增只读接口：

`GET /api/v1/people/search`

查询参数：`page / pageSize / q / role / cityCode / languageCode / skillCode / status / actualProject / workQ / workOrigin / verifiedWithinDays`。

管理前端“人才档案”页已使用结构化检索入口，展示条件、命中依据、未知信息和当前实际项目数。原人才详情与编辑路径不变。

隔离开发环境已单独运行新增 6 项核心测试通过；旧核心测试分批回归通过。统一 `run-core-tests.mjs` 在当前工具执行时限内两次于前八个文件后被外层中断，因此不把本地分批结果写成一次完整 229/229。完整类型、构建、PostgreSQL 和 Chromium 验收以当前 PR 最终 GitHub Actions 固定 head 为准。
